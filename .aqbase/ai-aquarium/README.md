# AI 어항 — 작은 마을

CoNAI 채팅 프로필을 주민으로 초대하는 개인 플러그인. 서버에서 산책과 대화를 진행하며 화면을 닫아도 마을은 계속 동작한다.

버전별 변경 내용과 각 기능의 상세 규칙은 [CHANGELOG.md](CHANGELOG.md)에 있다.

## 사건과 일자별 기억 (3.25.0)

3.25.1에서는 마을 채팅과 방송의 행동 묘사 스타일을 메뉴 버튼과 분리했다. 행동 묘사에 버튼 높이·여백·굵기·줄바꿈 금지가 적용되던 문제를 수정했으며 원문과 저장 기록은 바꾸지 않는다.

실행 중인 마을은 게임 날짜(00:00 경계)가 끝난 뒤 주민 자신의 프로필로 그날의 핵심 결과를 정리한다. GM은 자기 관점의 별도 기록을 정리한다. 사건이 한 개뿐이어도 다음 날 대상이 되며, 오늘의 사건은 최근 기억으로 유지한다. 긴 하루는 프로필 문맥에 맞춰 나눠 처리하되 같은 날짜 일지를 갱신하고 남은 사건이 있으면 **정리 중**으로 표시한다. 중지 중에는 모델을 호출하지 않고 재개 후 처리한다.

방문·도착·휴식·근무 시작 등 반복 상태는 소식/개인 기억에 쌓지 않고 판단 이력에 남긴다. 방문에 반복 기분 보상은 없으며 현재 장소는 방문 선택지에서 제외한다. 구매 등 자산 변화는 대상과 금액을, 제작은 접수가 아니라 실제 완성·수령/납품 결과를 기억한다.

**사건 기록**은 일지 요약을 먼저 보여 주고 근거 원문은 펼쳐서 확인한다. 장기 로어에는 지속되는 약속·관계 변화·중요 경험만 추출하며 빈 목록도 정상이다. 저장 실패는 원문과 처리 위치를 보존하고 재시도하며, 모델 실패가 반복돼도 사건을 자동으로 건너뛰지 않는다. 기존 원문·세이브는 유지하고 게임 날짜가 없는 옛 기록은 날짜를 추측하지 않고 별도로 정리한다. 기존 호스트/SDK 계약은 바꾸지 않으며 플러그인 업데이트가 필요하다.

## 메인 채팅 엔진 대화 (3.24.0)

**호스트 요구 사항:** 이 변경의 `pluginTools`·`roomKey`·`expectedThreadId`, `llm.room`·`llm.forgetRooms`, 실행 identity/전달 영수증을 지원하는 최신 호스트와 동봉 SDK가 필요해. 이전 호스트는 엄격한 입력 검증으로 400을 반환하므로 호스트를 먼저 업데이트해. 현재 manifest에는 최소 호스트 버전 필드가 없어서 임의 필드를 추가하지 않았어.

주민 대화와 방송 답변은 `mode:'profile'`로 실행한다. 프로필 도구·MCP·생성 프리셋·판단 프리셋·훅·로어·번역·문맥 설정은 일반 채팅과 같다. 별도 JSON 답변이나 어항의 before/after 판단은 없다. 호스트가 지원하는 네이티브 후속 답변은 같은 실행에서 기다려 빈 줄로 구분한 말로 기록한다. Codex의 후속 판단 지원 범위도 일반 Codex 채팅과 같다. 다음 발언자만 어항이 별도로 판단한다.

어항 교류·받은 요청 답변·대화 종료·상태 변경은 `pluginTools:['turn']`로 추가하는 `p_ai_aquarium_turn`만 사용한다. pause/inspect/lore 등은 자동으로 추가하지 않는다. 호스트가 전달한 `context.run`의 requestId/profileId/threadId를 활성 차례에 묶고 계정의 활성 슬롯, 마을/게임 설정 리비전과 기존 교류·동의·상태 규칙을 확인한다. 프롬프트에 권한 토큰을 쓰지 않는다. 종류별 동일 재시도는 결과만 돌려준다. 네이티브 도구의 프로필 허용 목록과 기존 권한·검토는 그대로다.

프로필 방은 슬롯 세대의 roomKey로 분리하고 제목에는 UUID 대신 슬롯 이름(roomTitle)을 붙인다. 초기화/삭제 전에 취소한 job이 terminal이 될 때까지 최대 10초씩 확인하고 마지막 영수증을 반영한 뒤 forgetRooms를 호출한다. 실패/이탈 경로에서 이미 취소 중인 작업도 함께 기다린다. 확인 시간이 지나면 삭제하지 않고 오류를 알린다. 자동화 발언만 있는 방은 자체 로어북·외관과 함께 정리하고, 네가 직접 쓴 메시지가 있는 방은 일반 채팅으로 남긴다. 정리 결과는 방마다 deleted/unlinked로 구분한다.

`llm.room`은 실행 잠금을 기다리지 않고 방을 조회한다. threadId가 바뀌면 요약·최근 16개 기억·로어를 다시 준비하며, expectedThreadId 실행은 사라진 방을 재생성하지 않는다. 작은 지시문·상황·장소·행동·참가자·도구 규칙은 매번 포함하고 기억/로어만 증분 전달한다. 취소 직후의 접수 응답이 아니라 terminal job의 마지막 delivery 영수증으로 커서·리비전을 병합해 늦게 저장된 입력도 반영한다.

교류·상태·종료 효과는 실행 즉시 소식/기억/판단 기록에 남는다. 발언 실패·취소가 이미 적용된 효과를 되돌리지 않으며 종료만 실행하고 말하지 않아도 정상 종료다. 완료된 첫 답변은 후속 실패나 후속 단계의 기한 만료로 버리지 않고 완료된 말과 미완료 안내를 표시한다. 첫 답변 시간 초과는 실패, 재우기/명시 취소는 항상 취소다. 번역된 프로필의 말은 호스트 표시 언어를 사용한다.

문맥/출력/시간 한도는 프로필 설정이고 명시적으로 고른 어항 답변 한도만 낮춘다. 방 FIFO 잠금 뒤 전역 실행 슬롯을 얻되 첫 답변 뒤에는 슬롯을 반환한다. 후속 지연은 전역 슬롯을 막지 않고 네이티브 후속 호출은 채팅 연결 제한을 따른다. 방 잠금은 후속/실제 중단 완료까지 유지하고 다음 실행은 완료 Promise를 기다린다. 어항 호출 예산은 실행 접수와 다음 발언자 판단에 적용한다. 이전 버전 text 대화/방송은 로드 때 폐기·취소하여 JSON을 대사로 기록하지 않는다.

## 주민 일상 판단 (3.23.0)

프로필 주민의 **일상 판단**은 생활·교류·장비·원정 출발과 받은 요청의 수락·거절을 한꺼번에 모델에 제시한다. 요청에 지금 답할지 다른 일을 먼저 할지도 모델이 정하며, 기존 요청 만료는 유지한다. 배고픔·피로·시간표는 문맥이지 행동 강제가 아니다. 코드는 자원·대상·경로 같은 실제 가능 여부만 검사한다.

**마을 관리 → AI 행동**은 `village` **일상·요청 판단**, `social` **대화·방송·신탁**, `combat` **전투·탐사** 세 줄이다. `agentVersion:5`에서 모든 `rules`를 `judge`로 이관한다. 새 슬롯의 모든 줄은 시간당·하루 무제한(`null`/빈 값)이며 최소 간격만 적용한다(일상 기본 20초). 0은 호출 중지다. 기존 저장 한도는 그대로 보존하고 사용자가 직접 바꾼다. 구형 combatAi off/boss도 모든 전투 차례의 모델 판단으로 바꾸며 설정과 AI 행동에서 전투 줄의 한도를 확인하라는 일회성 안내를 보여준다. 사용자가 확인하면 해당 저장 슬롯에 기억한다. 판단 모델 부재 시 자기 프로필의 chat으로 전환한다. 모델 부재·사용자 간격/한도·호스트 접수 부족·재시도·기억 정체에는 행동을 대신하지 않는다. 가능한 행동이 하나여도 모델은 실행하거나 기다릴 수 있다.

판단 모델에는 주민 자신의 추가 지시문, 마을 상황, 게임 시간 문구, `memory.decorate`가 채팅 경로에 제공하는 같은 기억을 전달한다. 새 호스트에서는 별도 문자/출력 상한을 만들지 않는다. 주민 상태 창의 **AI 판단 → 판단 기록**은 실제/게임 시간, 일상/요청 답변, 모든 제시 선택지(분류 포함), 선택 행동·상대·장소, 판단/채팅 방식·엔진·모델, 확률/신뢰도, 효과 또는 실패·대기 사유를 최신순 30개까지 세이브에 보존한다. 같은 이유의 연속 대기는 횟수로 합치며 어시스턴트 페이지 상태는 최근 5개를 받는다.

이 버전은 전투·탐사·근무·수면·보급·장비까지 모델 판단으로 바꾼다. 대기 주민의 공격·후퇴·식사·휴식을 코드가 대신하지 않는다. 전투의 몬스터 차례는 독립적으로 진행하므로 기다리는 동안에도 피해와 사망이 발생할 수 있다. 신탁의 class/skill kind가 유효하지 않으면 기존 직업·스킬을 보존하고 사유를 기록해 새 모델 답을 기다린다.

**호스트 호환성:** 기본 통합 목록은 생활 8개+교류 10개다. 판단 API의 선택지를 16개로 제한하는 호스트에서는 이 목록을 접수할 수 없어 주민이 사유를 남기고 기다린다. 전체 목록을 받는 호스트 업데이트가 필요하며, 그 전에는 일상 판단 줄을 같은 프로필의 채팅 모델로 설정할 수 있다. 플러그인이 선택지를 자르거나 일부 행동을 대신 고르지는 않는다.

## 문맥 예산 (3.22.4)

모든 텍스트 요청은 `server/llm-budget.mjs`의 `startBudgeted`로 접수한다. **프로필 설정이 기준**이다. 기본은 `maxTokens`를 보내지 않아 호스트가 프로필 최대 토큰을 그대로 사용한다. 기존 세이브도 한 번 **프로필 기본값**으로 이관한다. 이후 사람이 마을 관리 → 마을 → AI 답변 한도에서 숫자를 직접 고를 때만 추가 상한을 보낸다(`prepare.replyLength:0`은 프로필 기본값). GM·기억·조사·다음 화자에도 별도 고정 출력 상한을 두지 않는다.

문맥은 `profiles().context.contextTokens`와 `llm.measure`의 **실제 모델 한도만** 사용한다. 모르면 추정 문맥 크기나 여유분을 만들지 않고 그대로 보낸다. `measureInput`은 엄격한 측정 스키마에 맞춰 `requestId`, `mode`, `research`, `timeoutMs`, 플러그인 내부 필드를 제외한다. 측정이 있으면 먼저 실제로 재고, 없을 때만 한글/CJK/가나 1.5토큰·나머지 0.3토큰 추정으로 알려진 실제 문맥과 비교한다. 새 호스트의 접수는 설정된 출력 상한 전체가 아니라 네이티브 최소 여유(`min(설정 출력 상한, 256)`, 상한을 모르면 0)를 따른다. 전체 출력 예약 때문에 `available`이 음수인 것만으로 입력을 줄이거나 거절하지 않는다.

실제 문맥을 넘을 때만 필수 지시·선택지·스키마를 남기고 완전한 객체/사건을 선택한다. 선택 순서는 작업 자료 → 최신 기억 기록 → 개인 로어 → 세계관. 줄여야 할 때의 작업/최근/개인/세계 비율은 대화 `65/15/12/8`, 판단 `75/10/10/5`, GM `55/20/15/10`, 기억 `90/0/10/0`, 조사 `100/0/0/0`이다. 문맥을 모를 때 이 비율로 제한하지 않는다. 기억 추출에는 세계관을 넣지 않는다. 알려진 문맥의 첫 413은 실제 측정한 필수 입력/프로필 비용을 전체 문맥에서 빼고 선택 자료를 다시 맞춘다. 추가 축소만 선택 여유의 60%를 사용하며 최대 두 번 줄인다. 달라진 입력에는 새 ID를 쓰고, 접수 응답 유실에는 저장한 정확히 같은 입력·ID를 재사용한다. 알 수 없는 문맥은 추측하지 않는다. 호스트 본문 전송 413은 별도 사유로 표시하며 선택 자료만 한 번 줄인다. 플레이어/장면의 JSON 같은 문장은 필수 입력이고 여러 줄 발언도 한 기록으로 유지한다.

기억 정리는 입력 문맥에서 알려진 프로필 출력 상한을 남긴 뒤 완전한 사건을 고른다. 출력 상한이 없으면 필수 입력을 뺀 공간을 사건과 답변에 절반씩 나누지만 `maxTokens`를 만들지 않는다. 문맥을 모르면 정리 대상 전체를 보낸다. 내용·JSON 오류만 사건 수를 절반으로 줄여 1개까지 재시도한다. 이후에는 항목을 비우고 핵심 요약을 요청하지만 출력 토큰은 여전히 프로필 설정이다. 단일 사건의 내용 오류 3회는 커서를 한 사건만 넘기고 **사건 기록**에 원문과 사유를 보존한다. 사건 자체를 중간에서 자르지 않는다. 쿼터·인증·연결·시간 초과·대기열·조회 실패는 묶음/커서를 주민별로 보관하고 5초부터 최대 30분까지 지수 대기하며 사유를 표시한다. 기다리는 동안 다른 주민/GM을 순환 처리한다. 일시 조회 실패는 같은 작업을 확인하되 404/410과 시작 409는 같은 사건을 새 요청 ID로 접수한다. 모델이 권장 개수보다 많이 답해도 온전한 JSON을 거절하지 않는다. 새 호스트는 wildcard 번역을 청크로 나누며 이전 호스트는 요약만 번역한다.

비어 있는 기억/로어 몫은 작업 자료에 돌려준다. 합친 `history`는 저장하지 않고 접수 때 원본 기록으로 구성한다. 접수 확인 전 `_budget`/정확한 재전송 입력은 `llm_payloads`의 소유자·상태 종류별 압축 행으로 보관하고 tick 상태는 작은 참조만 갱신한다. 읽은 스냅샷은 참조별 캐시에서 복사하므로 매번 압축을 풀지 않는다. 스냅샷 누락/손상은 그 요청만 복구 필요로 표시하며 슬롯은 계속 열린다. 재구성한 입력에는 반드시 새 ID를 쓴다. jobId가 확인되면 원본 로어 목록과 전달 복사본을 버리고 사용하지 않는 행을 정리한다. GM 생활/공사/층 설계는 게임 검증 실패도 한 번 세지만, 시작 거절과 결과 없는 호스트 취소는 일일 사용량에 포함하지 않는다.

기억 묶음은 사건 사이 JSON 구분자를 포함해 계산하고, 선택 후 실제 호스트 측정으로 초과한 만큼 끝 사건을 빼며 최대 네 번 보정한다. 추정 차이 자체는 내용 실패 횟수에 포함하지 않는다. 떠난 주민/교체된 GM의 보류 작업·스냅샷·오류는 정리하되 사건 원문은 보존한다. 방송 대기 한도는 보류/실행 항목까지 포함하고 대기 중에는 로어 스냅샷을 만들지 않는다.

`llm.measure`가 있는 **새 호스트에는 플러그인 요청별 문자/바이트 상한을 적용하지 않는다**. 전체 HTTP/워커 본문(호스트 기본 5MiB, 설정 가능), 큐와 실제 프로필 문맥은 호스트가 검증한다. 이전 텍스트 호스트의 실제 전송 계약(메시지 16,000자·기억 32,000자·스키마 16KiB)에만 호환 처리를 유지하며 완전한 항목 단위로 선택한다. judge에는 임의 상태/필드 길이 제한을 덧붙이지 않고 호스트가 접수를 검증한다.

모델의 설명·목표·직업/스킬 이름·기억·로어·번역은 임의 글자 수로 자르거나 길다는 이유로 거절하지 않는다. 프로필의 실제 문맥/출력 설정과 호스트 전송 한도를 따른다. 페이지 스냅샷의 320,000자 자원 한도에는 원문을 바꾸지 않는 별도 compact projection을 사용한다. judgeTurn의 최대 40개 대화 항목은 호스트 계약이며, 목록·작업·검색 인덱스의 개수 한도는 저장/실행 자원 보호다. ID 형식·권한·수치·물리 용량 검사는 유지한다.

일반 GM 대화는 작은 관리 스키마와 한 번에 24개 관리 작업의 실행 예산을 쓴다. 대상·ID·권한·리비전·자원·동의 검사는 그대로다. 답변 대기의 프로필 기본값은 `timeoutMs`를 생략한다. 명시 대기만 호스트 범위로 적용한다. 전투의 별도 combatWait/combatDaily·규칙 대체는 제거했고 기존 하루 한도는 combat 행으로 합쳤다. 실패는 해당 주민/작업만 대기하며 재시도 시 유효한 새 요청 정체성을 사용한다. 접수 응답 유실은 같은 정체성으로 복구한다.

새 호스트의 텍스트 접수는 실행 네 개를 이유로 거절하지 않고 네이티브 큐에 대기시킨다. 플러그인별 대기 64개/입력 합계 64MiB, 인스턴스 공용 실행 네 개는 호스트 자원 보호이며 플러그인이 별도 큐나 제한을 만들지 않는다. 네이티브 awaited judge API의 네 개 동시 실행 보호는 별개다. 실제 대기열 가득 참/판단 접수 부족만 기다리고, 쿼터·인증·문맥·시간 초과·제공자·실행기·연결·불완전 JSON 오류는 분류와 원래 호스트 사유를 보여준다.

주민·GM·던전 오류 영역에 입력/출력/문맥·대기·축소 진단과 재시도/남은 호출 수를 표시한다. 조사는 요약·근거·의견 차이·다음 질문을 맨 앞에 완성하도록 요청하고 동등한 제목 서식을 허용한다. 출처 검증은 유지한다. 호스트의 네이티브 조사 후속 라운드·번역 내부 문맥과 알려지지 않은 모델 한도는 플러그인이 임의로 제한하거나 정확한 크기를 보장하지 않는다.

## AI 답변 대기

**마을 관리 → 마을 → AI 답변 대기**의 기본은 **프로필 기본값**이다. `timeoutMs`를 보내지 않고 프로필/연결/엔진의 설정과 호스트 작업 상태를 따른다. 기본 5분이었던 세이브는 이관하고 명시한 다른 값은 유지한다. 숫자를 선택할 때만 **5–30분**을 새 요청에 적용하며 플러그인은 상태 확인 여유 30초를 더 기다린다. GM·주민·방송·기억·던전 설계·신탁·원정/생활 판단·외형 설명·judge에 동일하게 적용한다. 어시스턴트의 `prepare.replyTimeoutMinutes:0`도 프로필 기본값이다.

자료 조사 창의 명시 제한 시간과 이미지 작업 만료는 별도 자원 보호다. 모델 요청의 기본 대기는 프로필/연결 설정을 따르며, 기다렸다는 이유로 행동을 자동 실행하지 않는다.

## 지도

기본 지도는 `shared/tiles.mjs`의 52×30 글자 배열이다(풀·길·광장·물·나무·건물·꽃밭·벤치·가로등·분수). 세이브마다 이 배열에서 시작해 크기·시설·공사 부지·설치 가구를 더한 **실행 지도**(`runtimeMap`)를 갖는다. 화면은 실행 지도를 칸 단위로 그리고(길·물가·꽃밭 테두리는 이웃 칸을 보고 그린다), 서버의 걷기·장소·경로(`canWalk`, `findPath`, `runtimePlaces`)도 같은 지도를 읽는다. 지도가 넓어지거나 시설이 생기면 화면이 다시 그린다. 생성된 시설 그림이 있으면 시설 칸 크기에 맞춰 아래쪽 출입구 줄에 붙여 그리고, 그림이 없거나 준비 중이면 기존 지붕 그림으로 그린다. 장소는 칸 영역이라 주민은 그 안의 빈 칸으로 가고, 한 칸에는 한 명만 선다. 지도를 바꾸면 `MAP_VERSION`을 올린다. 저장된 주민은 다음 로드 때 가장 가까운 빈 칸으로 옮겨진다.

말풍선은 말하는 주민 머리 바로 위에 꼬리를 달고 뜬다. 대화 중인 두 주민의 풍선은 서로 반대쪽으로 펼쳐진다. 주민을 고르면 엿듣기 범위(4칸)가 점선 원으로 보인다.

## 그림

주민 그림은 각 프로필의 이미지 도구·생성 프리셋·이미지 판단 항목으로 실행한다. 어항 전용 draw 행동·3분 제한·그림 설정·팔레트 배지는 없다. NovelAI는 한 요청에 `n_samples:1`을 사용한다. 별도의 **게임 그림**(몬스터·물품·층)은 기존 길드 설정을 그대로 사용한다. `server/village/draw.mjs`에는 게임 그림에 필요한 서비스 설정 검증만 남아 있다.

## 마을 앨범

주민 그림은 라이브러리 이미지 그룹 **AI 어항**에 모인다(없으면 처음 넣을 때 생성). 복사본은 만들지 않는다. 서버가 접수한 생성 작업을 3초 간격으로 따라가 그룹에 넣고, 새 그림은 월드 채팅에 "그림 N장을 마을 앨범에 걸었어"로 알린다. 1시간 안에 이미지가 나오지 않으면 버린다. 마을이 잠들어도 이어서 따라간다.

HUD의 앨범 버튼은 그 그룹을 `search_images`(그룹 필터)로 30장씩 읽어 masonry로 보여 주고, 화면에 들어오는 그림만 `get_media_download` → `api.media.open`으로 연다. `server/village/gallery.mjs`(서버)와 `page/village/album.js`·`page/styles/album.css`(화면)가 담당한다.

## 설치

`background.account`, 프로필 `appearance`, LLM `research` 실행 계약이 포함된 최신 CoNAI를 빌드·재시작한 뒤 새 패키지를 설치한다. 3.16의 자료 조사는 ZIP만 업데이트해서는 동작하지 않으며 호스트 업데이트도 필요하다. 3.17의 모든 프로필 엔진(직접 API·Claude Code·Codex·Pi) 조사는 그 계약이 들어간 최신 CoNAI가 필요하다. 3.18부터 조사의 도구 사용 횟수는 앱 전역 **도구 호출 반복 한도**를 따르므로, 그 설정이 들어간 CoNAI가 필요하다(이전 호스트는 생략한 상한을 8회·24회 기본값으로 제한한다).

```powershell
node scripts/build-plugin.mjs --local ai-aquarium
```

`build-output/local-plugins/ai-aquarium.zip`을 설정의 플러그인 관리에서 기존 패키지 위에 설치한다. 주민·대화 데이터는 유지된다. 페이지는 `/#/ext/ai-aquarium/village`다. 신뢰된 서버 모듈이 포함되며 소스와 ZIP은 Git/Docker에서 제외된다.

## 사용과 데이터

1. 주민으로 초대할 프로필과 마을 상황, 행동 간격을 설정하고 적용한다. 이미지 도구는 프로필 설정에서 연결한다.
2. '마을 깨우기'를 누르면 플러그인을 활성화한 계정으로 서버가 진행한다. 최대 3개 대화가 독립적으로 이어지며 호스트의 플러그인 4개 실행 슬롯을 함께 사용한다.
3. '마을 재우기'는 신규 진행을 멈추고 진행 중인 답변·기억 정리를 취소한다. 이미 접수된 그림은 그대로 완성된다.

## GM과 세계 만들기

GM(게임 마스터, 이전 이름 DM)은 세계와 던전을 함께 맡는 프로필 하나다. 세계 만들기 대화, 플레이어가 승인하는 무료 게임 관리, 자동 던전 설계·게임 그림·공사 심사·공공 계획(아래 **마을 생활**)을 맡는다. 주민의 판단은 GM이나 대리 프로필이 아니라 해당 주민 자신의 프로필이 맡는다. 생활 NPC는 규칙으로 움직인다. 앞으로의 단계는 [확장 계획](EXPANSION_PLAN.md)에 있다.

자율 모험(던전)을 꺼도 마을 생활과 GM의 게임 그림 외형 묘사·그림 처리는 계속된다. 원정 출발·전투·길드 의뢰 생성·새 탐험 결정은 멈추고, 이미 나가 있던 원정과 그림은 손대지 않고 보존한다.

새 마을의 첫 화면이나 이야기 탭의 'GM과 세계관 다듬기'에서 연다. 채팅 프로필 하나를 GM으로 고르면, GM이 대화하며 세계 이름·마을 상황·세계관 항목·첫 던전 층을 정해 오른쪽 카드에 모은다. 필수 항목이 차면 '이대로 시작'으로 슬롯 이름, 마을 상황, 세계관 로어북, 길드 GM과 첫 층에 한 번에 적용한다(`server/village/setup.mjs`, `page/village/setup.js`). 대화와 초안은 슬롯의 마을 상태에 저장된다.

세계가 정해진 뒤에는 게임 화면 오른쪽 아래의 GM 버튼으로 같은 대화를 이어 간다(`page/village/dm.js`). **적용 / 고쳐 줘 / 안 할래** 흐름을 유지하며 적용 전에는 조건부 제안으로 말하고 적용 카드에는 각 작업의 실제 결과와 실패 이유가 따로 남는다. 일부 실패한 제안을 통째로 성공이라고 표시하지 않는다. 같은 제안의 관리 작업이 하나라도 실패하면 사건 소식·주민 기억은 **건너뜀**으로 표시하고 기록하지 않는다. 결과·요약에는 내부 UUID 대신 이름·위치를 쓴다. 빈 제안은 새 카드를 만들지 않고, 이전 버전의 빈 카드도 성공이라고 표시하지 않는다.

### 플레이어의 무료 GM 관리

대상은 **화면의 이름 전체** 또는 짧은 ID로 지정할 수 있다. 예를 들어 `actorId: "QA LiteLLM Direct"`와 `actorId: "R1"`을 모두 받으며 대소문자·공백은 무시한다. 주민 R, NPC N, 시설 B, 물품 I, 층 F, 의뢰 Q, 공사 C, 템플릿 T, 그림 A 뒤에 번호가 붙는다. 원래 저장 ID도 계속 받는다. 이름이 같으면 후보와 위치·짧은 ID를 보여 주고 실패하며 부분 이름이나 비슷한 이름으로 추측하지 않는다. 제안 카드가 나오기 전에 실제 대상을 확인해 이름을 표시하고, 그 대상을 저장 ID로 고정한다. 짧은 ID는 그 대화의 조회 기준이므로 다음 대화에서는 새 목록을 따른다.

직접 부탁하고 **적용**하면 골드·재료·공공 금고를 쓰지 않고 즉시 실행한다. 별도 공사 심사나 자동 GM 하루 한도도 적용하지 않는다. 주민의 일반 공사·신전 발전 판단·자동 층 설계는 기존 경제와 한도를 그대로 따른다.

- **시설**: 신축은 빈 부지 자동 선택이 기본이며 플레이어가 직접 좌표를 말할 때만 좌표를 지정한다. "광장 옆"은 `near: "광장"`으로 가까운 유효 후보를 우선한다. GM에게는 후보의 가까운 장소와 방향도 알려 준다. 3단계까지 증축, 이름 변경, 이동, 철거를 지원하고 지도는 동/남쪽으로 8칸씩 총 세 번까지 확장한다.
- **공사**: 즉시 완공·취소. 남은 예치금·자재는 반환하고 이미 진행하며 쓴 몫은 유지한다.
- **NPC·주민**: NPC 재고·골드·직장, 주민 골드, 생활 물품과 장비의 가방/개인 창고 지급·회수. 골드의 "200 더 줘"는 `add: 200`, "50 빼 줘"는 `add: -50`이며 적용 시점 잔액에 더한 뒤 0~10억으로 제한한다. "잔액을 200으로 맞춰"처럼 명시한 요청만 `set: 200`으로 덮어쓴다. 결과는 전후 잔액을 보여 준다. 기존 저장 제안의 `gold`는 절대 잔액 의미를 유지한다. 장착 중인 장비는 회수하지 않는다.
- **물품·의뢰**: 기존 생활 템플릿의 이름·설명·외형으로 물품 생성(주민을 지정하면 함께 지급), 기존 물품 이름·설명·외형 편집, 길드 의뢰 등록·미수락 의뢰 취소.
- **던전·그림**: 다음 층 즉시 설계(입장은 이전 층 공략 후), 기존 층 이름·테마·몬스터/수호자 이름·전리품·외형 편집, 대상 그림 다시 그리기. 새 층 능력치 예산·최대 층 수는 유지한다.
- 기존 세계 이름·상황·로어·사건·다음 층 바람·모험 켜기/끄기·주민 지시문·하루 길이·잠도 지원한다. **사건은 소식·기억만**, **다음 층 바람은 미래 설계 요청만** 저장한다. 실제 시설·물품 변경은 관리 작업이 필요하다.

부지·출입구·지도 연결, 수량·보관 한도·ID 검사는 그대로다. 마지막 여관·신전은 철거할 수 없고, 진행 중인 생산·증축이 있는 시설은 먼저 작업을 마쳐야 이동/철거할 수 있다. 자동 부지 찾기는 경로 검사 12후보까지이며 못 찾으면 좌표를 지정한다. 주민·NPC 골드는 0~10억, 의뢰 취소는 사용자가 만든 미수락 의뢰만 지원한다. 임의 코드·새 게임 규칙·프로필/NPC 생성·자유 지형 편집·기존 층 구조/전투 능력치 변경은 지원하지 않는다. 한 카드에 최대 24작업을 순서대로 적용하며, 실패 항목은 되돌리고 다음 항목을 처리한다. 새로 만들어진 ID가 필요한 후속 작업은 다음 대화에서 요청한다.

세계 만들기에서 첫 층을 다시 적용해도 이미 탐험한 층의 **이름·테마·몬스터 이름·외형**은 바뀐다. 지도·전투 능력치·탐험 진척은 유지하며 적용 후 GM이 이를 알려 준다.

### 게임 그림 설정과 결과

같은 그림 설정 경고는 GM 답변에 한 번만 덧붙이고, 열린 GM 대화/세계 만들기 화면에서는 안내 배너 버튼 하나로 모은다. 카드·메시지마다 같은 버튼을 반복하지 않으며 설정이 해결되면 예전 경고의 버튼도 숨긴다.

길드 설정 → **게임 그림**의 `gameArt`가 기준이다. NovelAI를 골랐거나, ComfyUI의 워크플로우·글 입력칸과 자동 라우팅 서버가 사용 가능하면 새 층·몬스터·수호자·아이템 그림을 기존 큐로 자동 생성한다. NovelAI 연결 여부를 자동 감지하지 않으며 모든 요청은 `n_samples: 1`이다. ComfyUI는 기존 `list_workflows`와 `get_generation_routing_options`로 확인한다.

미설정/안 그림, 불완전하거나 사용할 수 없는 ComfyUI, 연결·인증 실패나 반복 접수 실패는 GM 답·카드와 **게임 그림 설정 열기** 버튼으로 알린다. 던전이 켜진 상태에서 GM 창을 열어도 미설정을 안내한다. 일시적인 상태 조회 오류는 설정 경고로 고정하지 않고 후속 성공 때 경고를 해제한다. 자동 그림은 `assetDaily`를 지키고, **GM 카드의 새 층·물품·외형 편집·다시 그리기**는 모두 그 한도에서 제외한다. 같은 외형에 이미 그림이 있으면 재적용으로 다시 생성하지 않는다. 교체된 진행 중 작업은 호스트에 취소를 요청한다. 그림은 비동기 작업이며 완성 전에는 기존 그림을 유지한다. 게임 조작이 무료라는 뜻이지 외부 서비스 요금까지 무료라는 뜻은 아니다.

페이지 어시스턴트는 `gm_open`으로 조회하고 `gm_prepare`로 요청 문구만 준비한다. 보내기와 제안 적용은 사람이 누른다. `rpg_open`의 `settings` 탭은 기존 게임 그림 설정으로 이어진다.

마을 GM은 하나다(길드 설정의 GM이 기준이고 대화 GM이 따른다). GM은 주민처럼 기억·장기 로어북·기억 정리를 갖되, GM 프로필 ID의 음수를 키로 써서 같은 프로필의 주민 기억과 분리된다(`dmKey`, `server/memory/memory.mjs`). 대화·층 확장·그림 묘사 요청은 모두 `memory.decorate`를 거친다. GM 창의 기억 버튼으로 연다.

화면 이름만 GM으로 바뀌었고 기존 세이브와 연결을 위해 설정 키(`dmProfileId`, `dmDailyLimit`), 요청·작업 ID, 화면 요소 ID(`dm-*`)와 내부 이름(`dm`)은 그대로 둔다.

## 마을 생활

새 마을은 **여관과 신전**만 있는 지도에서 시작한다. 행상·여관 조리사·마을 건축가는 일반 NPC로 기존 영업/생산 규칙을 따른다. 주민 모델은 조리사 근무(20초, 4G), 식사·구매·제작·장비 등의 실제 대상과 비용을 보고 고른다. 잡화점이 생기면 물약·장비 구매 선택지가, 길드가 생기면 길드의 의뢰가 열린다. 자동 보급·자동 착용·중복/창고 초과 자동 판매는 없다. 이미 있던 세이브의 시설과 물품은 보존한다.

HUD 오른쪽 위의 **생활** 버튼, 주민 빠른 메뉴의 '생활', 지도의 시설이나 NPC를 누르면 생활 창이 열린다(모험을 켠 동안 길드·잡화점은 기존 길드 창을 열고, 신전은 언제나 시설 상세의 헌금 화면을 연다. 거기서 '길드에서 신관·직업 보기'로 길드 창에 갈 수 있다). 창 위쪽에서 행동할 주민과 수량(1–99)을 고른다. 마을에 돌아온 주민(마을·휴식 중)만 행동할 수 있다. 규칙은 서버의 `server/rpg/life.mjs`와 `shared/life.mjs`가 정한다.

- **주민 생활**: 가방과 창고의 물품 묶음(같은 물품은 수량으로 쌓인다), 진행 중인 작업, 공공 금고 기부. 물품마다 사용(따뜻한 차: HP +8·MP +4), 팔기(반값, 영업 중인 상대의 남은 자금 안에서), 보관·꺼내기(기본 보관함은 물품당 99개, 창고 시설은 단계당 200개 더·이용료 1G), 자재 기부, 납품, 가구 설치(지도에서 풀밭 한 칸)를 한다.
- **상점·NPC**: 다람 상인(상인)·생산자(새 마을은 여관 조리사, 이전 세이브는 찻집 장인)·마을 건축가(건축가). 지도에 점선 테두리 토큰으로 보이며 각자 근무 시간에 자기 시설로 간다. 역할·영업 상태·남은 재고·자금을 보여 주고 사기·팔기·납품·근무(찻집 일 20초, 임금 4G)를 한다. 재고와 자금은 유한하다. 마을이 깨어 있는 5분마다 NPC 자금 +30G(최대 200G), 기본 재료 +5개(재료당 최대 40개)씩만 보충된다.
- **시설**: 소유(공공 또는 개인과 소유주), 단계(최대 3), 크기·출입구, 생성 그림, 일하는 NPC, 서비스. 공방·찻집은 제작(재료·도구·이용료), 주택·여관은 휴식(2G, HP·MP 회복), 창고는 보관. 이용료와 기존 여관비는 개인 시설이면 소유주에게, 공공 시설이면 공공 금고로 간다.
- **신전 발전 헌금**: 신전 시설에서 주민·금액을 고르면 공공 금고와 누적 헌금(`life.donations.total`)에 반영된다. GM이 기존 예산과 제약 안에서 발전안을 검토하며 즉시 정해진 보상을 주지 않는다. 모델이 신탁 방문을 골랐다는 이유로 별도 헌금을 자동 차감하지 않는다. 공공 금고 기부와 신전 발전 헌금은 서로 다른 기록이다.
- **공사·공공**: 잡화점·모험가 길드·공방·찻집·주택·창고 신축, 같은 종류 시설의 증축, 동쪽·남쪽 인접 구역 개방(8칸씩, 최대 세 번, 한 번에 하나). 종류·자금(개인/공공)·부지(좌표 입력 또는 '지도에서 고르기')를 정하고 **견적 받기**를 누르면 서버가 비용·자재·깨어 있는 공사 시간·부지를 확인한 견적을 보여 준다(예약하지 않음). **공사 신청**을 누르면 골드와 자재를 예치하고 GM 심사를 기다린다.

공사는 GM 심사 대기 → 승인(착공 대기) → 공사 중(진행률) → 완공 순서다. GM이 거절하거나 착공 전에 취소하면 전액, 착공 뒤 취소하면 아직 쓰지 않은 골드와 자재만 돌려받는다. 공사비는 진행에 따라 건축가에게 지급되고, 건축가가 없으면 소모된다. 개인 자금으로 지은 시설은 신청자 소유·수입이고, 공공 자금 시설은 공공 소유다. 증축은 시설의 소유 방식대로만 신청할 수 있고 개인 시설은 소유주만 증축한다. 대기 공사는 여덟 개, 시설은 30개, 설치 가구는 40개까지다. 시설은 빈 풀밭에만 지을 수 있고 길과 출입구로 가는 길을 끊는 부지는 거절된다.

생산·공사·NPC 이동·보충은 마을이 깨어 있을 때만 진행되고, 잠든 동안의 시간을 몰아서 따라잡지 않는다. 거래와 신청은 잠든 마을에서도 할 수 있다. GM 프로필이 있으면 GM이 대기 공사를 심사한다. 던전 층 설계와 공사 심사는 각각 별도 일일 한도를 가지며, 두 한도의 값은 `dmDailyLimit`을 따른다. 자율 공공 계획(신전 헌금 판단)은 이들과 별도로 하루 한 번까지만 요청하고, 마을이 깨어 있는 시간이 5분 이상·공공 금고 30G 이상 또는 판단 대기 헌금이 있고·대기 심사가 없을 때만 시도한다. 생활 요청은 시작 시도부터 한도를 차감하므로 빈 제안이나 실패도 무제한 반복하지 않는다. GM이 없거나 공사 심사 한도를 소진하면 신청은 대기 상태로 남고 착공 전 취소하면 전액 돌아온다. 주민 일상 판단은 village 줄에서 사용자가 정한 간격·호출 한도를 따르고 생활·교류 선택지를 함께 모델에 제시한다.

생활 행동은 모두 `life-action` 요청 하나로 가며, 화면은 같은 작업을 다시 보낼 때 같은 요청 ID를 쓴다. 요청 기록은 의뢰와 함께 슬롯당 최근 30일·최대 10,000건을 유지하며, 이 기간에 응답을 못 받고 같은 요청을 다시 보내도 두 번 결제하지 않는다. 만료되어 삭제된 ID를 나중에 재사용하는 것은 이 보장 밖이며 새 작업으로 실행될 수 있다. 시설·물품 그림 키는 `building:<id>:<designRevision>`, `life-item:<id>:<designRevision>`이고 증축이 끝나면 새 그림을 받는다.

생활 타이머 진행은 최대 5초 단위로 저장하고 변경 작업·일시정지 전에는 쌓인 진행을 먼저 반영한다. 비정상 종료 시 아직 저장되지 않은 최대 5초의 진행이 유실될 수 있으며, 재시작 후 종료 시간을 소급하지 않는다. 생활만 바뀐 저장은 던전 다시보기를 만들지 않는다. 단순 거래·생산 기록은 주민 기억을 반복해서 채우지 않는다.

## 자료 조사와 토론

HUD의 **조사** 버튼으로 연다. 사람이 주제, 읽을 공개 게시글 ID(1–8개), 참여 주민 2–3명(프로필에 정해진 엔진 그대로), 토론 회차(1–3)를 정하고 **조사 시작**을 누른다. 주민 한 차례의 도구 사용 횟수는 플러그인이 정하지 않고 앱의 **도구 호출 반복 한도**(설정 › 채팅 › 자원 › 도구 사용, 기본 50)를 따른다. **제한 시간**을 펼치면 한 차례(기본 5분)·전체(기본 30분) 제한 시간을 정할 수 있다. 창은 시작 전에 실행할 차례 수와 시간을 보여 준다. 앱 한도에 닿은 주민의 발언은 부분 발언으로 표시되고 다른 주민의 차례는 이어진다. 이전 세이브의 호출 상한은 불러올 때 버리고 제한 시간만 남긴다. 사용량은 엔진이 알려 준 값만 그 이름대로 보여 준다(직접 API는 API 호출, Claude Code·Pi는 에이전트 차례, Codex는 집계 안 됨). 호출·차례 수는 금액이 아니며 실제 비용은 프로필의 엔진과 요금제에 따라 다르다. 서버(`server/research/`)가 지정한 글만 읽게 하고, 화면(`page/village/research.js`)은 진행 상태·회차·실제 호출 수·실패·중단·근거 없음, 실제로 읽은 근거(누르면 게시판의 그 글로 이동), 주민 발언을 보여 준다. 결과는 검증되지 않은 초안이며 자동으로 게시하지 않는다. **결과를 검토 요청으로 보내기**를 누르면 게시판의 문서 변경 제안(새 문서, `draft`)으로 들어가고 저장은 게시판의 기존 검토에서 한다(지식 기능·글쓰기 권한 필요). 조사 뒤 근거 글이 바뀌어 거절되면 **이 주제로 다시 준비**로 같은 입력을 다시 채워 새로 조사한다. 조사 대상은 사람이 지정한 게시글뿐이다.

마을 관리 → 마을 → 화면의 **생활 중심**은 길드 버튼과 LIVE 표시만 숨긴다. 던전 설정과 기록은 그대로다.

조사는 주민 프로필에 정해진 기존 엔진(직접 API·Claude Code·Codex·Pi)을 그대로 쓴다. 프로필 설정이 조사에 맞지 않으면 앱이 실행 전에 이유와 함께 거절하고 창에 그 사유를 보여 준다. 주민 차례마다 앱의 도구 호출 반복 한도를 적용하고, 토론 후 요약 1회(도구 없음)를 예약한다. 요약은 설정된 GM 또는 첫 참여 주민이 맡으며 요약·근거·의견 차이·다음 질문을 정리한다. 실제 모델 사용료는 게임의 골드·기부와 별개다.

활동은 마을이 깨어 있을 때만 진행하며 잠들기·슬롯 전환·초기화 시 중단한다. 참여 주민은 활동 중 일상 대화와 겹쳐 실행하지 않는다. 슬롯별 마지막 활동만 보관하고, 남길 결과는 게시판 검토 요청으로 보낸다. 파일·미디어 조사와 자율 주제 발굴은 아직 지원하지 않는다.

## 세이브 슬롯

마을 꾸리기 → **세이브 슬롯**(또는 HUD 왼쪽 위의 마을 이름)에서 계정당 최대 5개의 마을을 관리한다. 슬롯마다 주민·설정·대화·주민 기억·세계관 로어북·길드 진행·다시보기·앨범 그룹이 따로 저장된다. 서버는 지금 슬롯만 진행하고, 슬롯을 바꾸면 지금 마을을 먼저 재운다.

- 다른 마을: 슬롯 목록에서 '이 마을로 바꾸기'.
- 같은 주민으로 새로 시작: '지금 설정으로 새 슬롯'. 주민 구성·지시문·설정·세계관 로어북·길드 운영 설정과 역할만 가져온다.
- 완전히 새로: '빈 새 슬롯'.
- 지금 슬롯을 처음부터: '처음부터 다시 시작…' 뒤 슬롯 이름 입력. 설정과 세계관은 남고 진행만 지운다.

저장 키는 슬롯 1이 계정 ID(기존 데이터), 나머지가 `계정ID#번호`다(`server/village/slots.mjs`). 모든 마을 테이블이 같은 `owner` 열을 쓰므로 슬롯 삭제·초기화는 그 키의 행만 지운다.

모델이 정한 목적지까지 걷는 물리 경로는 코드가 계산한다. 일상·요청 답변·대화와 기억 정리에는 모델 사용량이 발생한다. 페이지는 보이는 동안에만 상태를 조회하고, 숨김·종료만으로 서버 진행을 멈추지 않는다.

주민·상황·위치, 월드 채팅(대화 200개·사건 120개), 주민별 기억·세계관 로어북은 플러그인 SQLite에 계정·세이브 슬롯별로 저장한다. 처리한 원문은 최근 200줄을 유지하고 미처리 원문은 정리 성공 전에 삭제하지 않는다(3.8의 활동 제한 적용). 호스트 호출 전에 요청 ID를 저장하며 불확실한 시작 응답은 같은 ID로만 재확인한다. 플러그인 제거는 전용 데이터도 삭제한다.

## 주민 상태와 AI 행동

주민의 **상태·관계** 창에서 목표·상태·관계·대화·요청과 실제 판단 모델/채팅 모델·엔진·프리셋·판단 기록을 본다. 상태 값과 관계는 사람이 저장하며 숫자는 정의 범위를 따른다. 프로필 고정 필드는 모델이 바꾸지 못한다. 직접 편집하지 않은 관계 이름은 유지한다. 요청의 답변 여부·수락·거절은 모델이 정하고 화면에서는 취소할 수 있다. 판단 오류와 기억 정체는 별도 대기 사유로 보여 준다. 규칙 행동 대체 모드는 없다.

**마을 관리 → AI 행동**에서 일상·요청, 대화·방송·신탁, 전투·탐사의 판단 방식과 간격·시간당·하루 한도를 정한다. 모두 자기 프로필의 모델을 쓰며 규칙 모드나 한도 초과 시 행동 대체는 없다. 대화 차례/동시 대화 한도, 행동 목록, 상태 정의도 같은 창에서 관리한다. 기본 행동 효과는 고정이고 추가 행동은 서버의 검증된 효과만 사용한다. 프로필 상태 정의는 읽기 전용이다. 어시스턴트의 prepare/resident_prepare는 초안만 준비하며 사람이 적용한다.

## 어시스턴트와 검증

### 3.23 서버 계약: 자율 주민

**분류·비용 계약**: `village`는 출발과 받은 요청의 답변 여부를 포함한 일상 선택, `combat`은 실제 전투·던전 탐사, `social`은 대화·방송·신탁 생성이다. 모델 접수 시도마다 예약하며 busy·모델 없음 등 미접수는 같은 예약을 환불한다. 실패한 완료 작업의 재시도는 새 요청 ID, 접수 응답 유실은 기존 ID를 사용한다. 한도나 모델을 기다리는 동안 주민 행동을 대신하지 않는다.

**오류 표시 계약**: 주민 `agentError`는 마을 판단/대화 오류만, 새 `combatError: string|null`은 전투 판단 오류만 나타내. `rpg.actors[].combatError`에도 같은 값을 제공하며 성공한 전투 선택 뒤에는 지워. 전투 오류를 주민의 일반 재시도 대기 표시로 사용하지 마.

**교류 입력 보강**: `act`/자율 교류의 물품 요청(`id:"request",kind:"item"`)과 물품 선물(`id:"gift",kind:"item"` 또는 gift의 기본 종류)은 생성 시 유효한 stackable `item` ID가 필수야. 골드 선물은 `kind:"gold"`를 명시해. 누락된 item을 골드로 해석하지 않으며 기존 잘못된 대기 요청도 수락 시 failed로 종료해.

**정체·상태 보강**: 기억 정체에는 새 모델 판단을 기다려. 식사·휴식으로 대신하지 않아. 재개 때 완료된 답부터 확인해. 채팅의 상태 제안은 기분·사교 만족·추가 상태·프로필 상태 필드만 대상으로 하며 배고픔/피로는 물리적인 시간 변화와 검증된 행동 효과로 바꿔.

슬롯의 RPG 설정에 `statusDefs`, `actionCatalog`, `deciders`, `conversationMaxTurns`(기본 8, 2–24), `maxConversations`(기본 3, 1–3)를 저장하고 일반 `state.settings`에도 투영해. `agentVersion:5`로 이관하며 저장된 모든 `rules`는 `judge`로 바꿔. 기존 대리 프로필 설정은 없애고 자기 프로필만 써. 별도 combatDaily는 기존 combat 하루 상한과 작은 쪽으로 합쳐 보존하며 combatAi/off/boss, combatWait, autoSupply는 없애. 구형 off/boss 이관 안내의 사용자 확인 상태도 슬롯에 저장해. 새 기본값의 시간당·하루 한도는 null(무제한)이지만 기존 저장 숫자는 바꾸지 않아. 어시스턴트는 `unlimitedHour`/`unlimitedDay`로 해당 한도를 지울 수 있어.

모델 입력은 공통 JSON 경계에서 정리하고 호스트 오류의 숫자 `status`로 접수 거절을 구분해. 400·403·404·409·413·429만 접수 거절로 환불하며 408 시간 초과·제공자 오류는 호출로 남겨. 409는 새 요청, 429는 짧은 고정 재시도이고 일상 판단 실패 뒤에는 실패 완료 시점부터 사용자 간격을 지켜. 방송 판단은 비차단 실행/조회와 5분 만료를 사용하고 실패·취소된 작업은 새 요청으로 판단해. 신탁 한도 대기는 공유 GM 대기열을 점유하지 않아. 대화 사전 판단·발언·사후 판단·다음 발언자 선택은 실제 모델 호출마다 시간당·하루 한도를 사용하고, 최소 간격만 한 차례에 한 번 적용해. 한도·끝난 답변 오류·반복 접수 실패로 다음 차례를 진행할 수 없으면 종료 이유를 양쪽 주민에게 기록하고 대화를 풀어 줘. 큰 판단 입력과 선택지 카탈로그는 payload 참조만 매 틱 저장하고 전체 기록은 주민 창에서만 조회해. 수면·휴식의 종료 조건도 모델이 골라 조건이나 관련 사건 전에는 재판단하지 않고, 사건이 와도 자동 기상하지 않아.

- **판단**: `deciders.combat/social/village = {decider:"judge"|"chat", minInterval, maxCallsPerHour, maxCallsPerDay}`. 간격은 실제 초, 시간당은 주민별 게임 시간, 하루는 UTC 실제 하루 슬롯 공용 한도야. 기본 간격은 combat/social 1초, village 20초이며 세 줄 모두 시간당·하루 무제한(null/빈 값)이야. 저장된 숫자 한도는 보존하고 0이면 호출하지 않아. village는 요청 답변 여부를 포함한 일상·출발, combat은 전투·탐사, social은 대화·방송·신탁이야. 실제 모델 호출마다 예약·환불은 같은 경로를 써. judge 일상 선택은 수량이 필요한 교류를 고른 경우에만 그 행동의 유효 범위로 수량/가격 후속 판단을 요청해. 이 추가 호출도 village 간격·한도를 적용하며 기다리는 동안 이전하지 않아. judge 모델 부재 시 자기 chat으로 전환하고 실제 프로필 설정을 따라. 전투 응답 대기에는 해당 주민만 행동하지 않으며 몬스터는 계속 진행해.
- **상태 정의**: 최대 16개 `{id,name,description,kind:"number"|"choice",min,max,initial,values,perHour,step,low,high,lowHint,highHint,enabled,builtin}`. 기본 기분·배고픔·피로·사교 만족이 있고 값은 주민마다 달라. 숫자는 범위 안으로 제한하고 **모델 제안·사용자 정의 효과**만 step으로 제한해. 검증된 음식·휴식·수면·시간 규칙은 step:0이어도 정상 적용해. 프로필 `statusBlocks`의 정의는 읽기 전용이야. valueReadonly 필드는 모델·사용자 정의 효과가 바꿀 수 없지만 사용자/GM의 명시적인 값 편집은 허용해. chat이 스스로 쓴 probability를 judge 결과로 신뢰하지 않으며 chat 상태 제안에는 step만 적용해.
- **행동**: 개수 제한 없이(같은 분류 안 ID 중복만 거절) `{id,category,label,description,enabled,builtin,effect}`. 설명은 실행되지 않아. custom effect는 damage 0–2, guard 0–0.75, heal 0–0.3, fleeChance 0–1, mpCost 0–20, affinity ±20, actorStatuses/targetStatuses의 숫자 증감 ±30, duration 5–300초, place, needsAcceptance, transfer(none/item/gold), amount 1–100만 사용해. combat은 공격/스킬/방어/물약/도망, social은 대화/선물/부탁/청혼/칭찬/논쟁/다툼/초대/사과/거래, village는 식사/휴식/수면/일/장보기/방문/제작/기부가 기본이야.
- **교류**: 수락 때 잔액·재고를 다시 확인하고 효과와 종료 상태를 한 트랜잭션에 반영해. 기한(실제 10분) 초과·당사자 퇴장은 expired, 수락 효과 실패는 failed, 사용자/GM 취소는 cancelled야. 실패한 수락은 물품·골드·상태를 일부만 이전하지 않아. 모든 종료 요청은 재응답해도 재실행하지 않아. 관계의 사용자/GM 명시 label은 일반 호감 변화로 덮어쓰지 않고 청혼 수락 같은 명시적인 관계 사건만 바꿔.
- **대화**: 각 차례 전에 profile judge preset의 금지 행동·지시를 반영하고, 뒤에 followUp과 maxConsecutive를 적용해. 다음 발언자는 자신의 judge room.next 지침·문턱으로 참여자/4칸 안 주민/종료 중 골라. `say`, `act:{id,target,item?,amount?,kind?,detail?}`, `reply:{requestId,answer:"accept"|"refuse",reason?}`, `end`를 받으며 최대 차례를 넘지 않아. 대화 밖 대기 요청도 받는 주민의 판단 차례에서 답해.
- **정체 표시**: 기억 정리가 밀리면 대화를 종료·취소하고 새 AI 판단과 **던전 진행도 잠시 멈춰** 새 사건이 원문 보관 한도를 넘지 않게 해. 마을 이동·식사·휴식·생산은 계속돼. 기억 정리는 대화와 독립된 `world.summary` 한 작업으로 계속 진행해. routine rules 생활은 기억 줄을 만들지 않아. `memoryBacklogged/memoryError`, 주민 `agentError/agentReadyAt`으로 이유를 보여줘.

3.21.1부터 자율 행동 재시도 기록은 슬롯 상태의 별도 512건/최대 24시간 순환 기록으로 보관해(먼저 도달한 한도로 정리). 판단 시각·확률·신뢰도는 행동 동일성에 넣지 않아. 3.21의 기존 자율 기록도 분리하며 플레이어 생활·의뢰·GM 명령의 30일/10,000건 보장은 그대로 유지해.

**어시스턴트 사용자 정의 상태 효과**: `prepare.actionCatalog[].effect.actorStatuses`와 `targetStatuses`는 `[{id:"trust",delta:5}]` 형태로 보내. 각 배열은 최대 16개, ID는 `/^[a-zA-Z][\w-]{0,39}$/`, delta는 -30..30이야. 호스트 초안 스키마가 동적 객체 키를 지원하지 않아 배열로 전달해. 서버 `agentSettings()`는 이 배열과 기존 `{trust:5}` 맵을 모두 받아 같은 맵으로 정규화해. 적용 시 현재 슬롯(같은 설정 패치의 statusDefs 포함)의 숫자 상태 ID인지 검사하며 없는 ID는 거절해. 상태 응답과 저장의 effect는 기존 맵 형식을 유지해.

페이지는 기존 요청 채널로 아래 `op`를 보내면 돼. 변경 응답은 모두 기존 `state` 전체 모양이야. 별도 MCP 변경 도구는 없어.

| op | 입력 | 응답/의미 |
| --- | --- | --- |
| `state`, `agent-state` | `{op,after?}` | 기존 상태 + 아래 자율 주민 필드 |
| `agent-configure` | `{op,saveId:state.save.id,revision:state.agentSettingsRevision,settings:{statusDefs?,actionCatalog?,deciders?,conversationMaxTurns?,maxConversations?}}` | 정의/카탈로그 배열은 전체 교체; 생략한 기본 항목은 비활성화. 슬롯·설정 충돌은 거절 |
| `resident-status-set` | `{op,saveId:state.save.id,profileId,values:{상태ID:숫자또는선택문자열}}` | 해당 주민 값만 부분 변경·범위 제한 |
| `relationship-set` | `{op,saveId:state.save.id,from:profileId,to:profileId,affinity,label?}` | 쌍의 관계 변경 |
| `request-cancel` | `{op:"request-cancel",saveId:state.save.id,requestId,reason?}` | 대기 교류를 cancelled로 종료. 재시도는 효과 없음. reason은 최대 200자로 제한. 응답은 전체 state |
| `configure` | 기존 입력 + 위 설정 필드 | 기존 화면 호환; 원래 마을 설정과 함께 적용 |

추가 상태 필드:
- `statuses:{definitions,residents:[{profileId,values,definitions}]}`, `relationships:[{a,b,affinity,label}]`
- `pendingRequests:[{id,from,to,action,item,amount,kind,place,detail,status:"pending"|"accepted"|"refused"|"expired"|"failed"|"cancelled",createdAt,expiresAt,resolvedAt?,reason?,result?}]` (최근 100개). 취소 버튼은 pending에만 표시해. `place`는 초대·동행할 실제 장소 이름이야.
- `conversations:[{id,participants:number[],speaker,turn,maxTurns,nextAt,thinking,lines:[{from,name,text}]}]`
- `actionCatalog`, `deciders`, `agentSettingsRevision`; 주민마다 `goal,statuses,statusDefs,agentError,combatError,agentReadyAt,agentRoute,judge,profileEngine`

GM 검토 카드의 `request-cancel`, `status-definition`, `status-remove`(기본 정의는 비활성화, 추가 정의는 제거), `status-set`, `relationship-set`, `action-definition`, `agent-settings`도 같은 검증/실행 함수를 사용해.

페이지 연결은 상태 확인·주민 선택·설정 초안·일시정지를 제공한다. 설정 적용과 깨우기는 사람이 화면에서 실행한다. 생활은 `ai-aquarium.life_open`(생활 창 탭과 주민·NPC·시설 선택, 조회만)과 `ai-aquarium.life_prepare`(생활 행동 하나의 초안, 공사는 견적 포함, 신전 발전 헌금 `temple-donate` 포함)를 쓴다. 초안은 생활 창 위쪽에 남고 사람이 **실행**이나 **공사 신청**을 눌러야 적용된다. 페이지 상태의 `life`에 주민 가방·창고, NPC 재고·자금, 시설과 잡화점·길드 건설 여부, 공사, 납품 의뢰, 공공 금고, 발전 헌금(누적·판단한 몫·대기·판단 상태)과 지금 초안이 있다. `p_ai_aquarium_inspect`와 `p_ai_aquarium_pause`는 호출 계정의 마을을 조회·정지한다. `p_ai_aquarium_life_quote`는 예치 없이 공사 견적만 조회한다. 외부 MCP에서 생활 거래·공사를 직접 실행하는 도구는 제공하지 않는다. 조사는 `ai-aquarium.research_open`(조회)과 `ai-aquarium.research_prepare`(주제·게시글·주민·회차 입력 초안)를 쓰고, 시작·중단·검토 요청은 사람이 누른다. 게임 내부 주민의 자율 행동과 플레이어의 직접 실행은 이 외부 어시스턴트 초안 경로와 구분한다.

## 파일 구성

`plugin.json`과 `index.html`만 패키지 루트에 두고, 나머지는 실행 위치별로 나눈다. ZIP을 만들 때 SDK(`conai-plugin.js`·`.css`)가 루트에 추가된다.

- `shared/`: 서버와 화면이 같이 읽는 규칙. `tiles.mjs`(마을 지도 타일 배열), `clock.mjs`(마을 시계), `schedule.mjs`(근무 시간), `rpg-systems.mjs`(경제·원정 기억·전투 추정), `village-settings.mjs`(설정 범위·기본값·엿듣기 범위), `speech.mjs`(대사 정리), `resident-instructions.mjs`(주민 지시문).
- `server/main.mjs`: 서버 모듈 진입점. 0.5초마다 마을을 한 단계 진행한다.
- `server/village/`: 마을. `village.mjs`(진행 루프와 조립), `store.mjs`(저장·대화 기록), `talk.mjs`(네이티브 대화와 실행에 묶인 효과), `memory-pass.mjs`(기억 정리), `broadcast-chat.mjs`(방송 채팅 답장·반응), `errands.mjs`(출근·잠·원정 길), `requests.mjs`(화면 요청과 어시스턴트 도구), `slots.mjs`(세이브 슬롯·방 세대), `world.mjs`(장소와 이동), `draw.mjs`(게임 그림 서비스 설정 검증), `gallery.mjs`(앨범 수집), `text.mjs`·`constants.mjs`.
- `server/memory/`: 주민 기억(`memory.mjs`), 로어북(`lore.mjs`), 번역 표시(`bilingual.mjs`).
- `server/rpg/`: 자율 모험. `rpg.mjs`(설정·진행·조립), `rules.mjs`(탐험·전투 규칙), `dungeon.mjs`(던전 생성·시야·경로), `pending.mjs`(GM·판단·신탁·원정 결정 요청), `prompts.mjs`(요청 문구), `answers.mjs`(응답 형식), `combat.mjs`(전투 턴 요청), `assets.mjs`·`game-art.mjs`(게임 그림), `store.mjs`(저장), `view.mjs`(화면용 상태), `replay.mjs`(다시보기 기록).
- `page/main.js`: 화면 진입점. 공유 상태, 서버 폴링, HUD, 어시스턴트 연결.
- `page/village/`: 지도 화면(`scene.js`, 땅·하늘은 `map-paint.js`), 생활 창(`life.js`), 자료 조사 창(`research.js`), 주민 목록(`party.js`), 빠른 메뉴(`quick-menu.js`), 월드 채팅(`chat.js`), 설정 창(`settings-menu.js`), AI 행동·상태 정의 탭(`agents.js`), 주민 상태 창(`resident.js`), 세이브 슬롯 탭(`saves.js`), 프로필 이미지(`faces.js`), 앨범(`album.js`), 기억 창(`memory-view.js`).
- `page/guild/`: 길드 창. `guild.js`(창과 공유 상태), `actors.js`(모험가), `quests.js`(의뢰), `shop.js`(상점), `zones.js`(던전 층 지도), `settings.js`(모험·전투·역할 설정), `parts.js`·`common.js`(공통 부품과 라벨).
- `page/broadcast/`: 방송. `broadcast.js`(창·재생 루프·카드), `channels.js`(채널 목록), `town.js`(마을 카메라), `replay-scene.js`·`chat-lines.js`(다시보기 장면과 채팅 줄).
- `page/ui/`: 공용 화면 부품(`dom.js`, `portrait.js`, `tip.js`, `hold.js`, `draw-picker.js`, `speech.js`, `bubble-layout.js`, `floor-paint.js`, `art-cache.js`).
- `page/styles/`: `index.html`이 순서대로 불러오는 스타일. 색 토큰은 `style.css`의 `:root` 한 곳에 있다. SDK `conai-plugin.css`는 `<link>`가 아니라 `style.css` 첫 줄의 `@import … layer(sdk)`로 낮은 캐스케이드 레이어에 들어가므로, 플러그인 규칙이 선택자 우선순위와 상관없이 SDK 기본 규칙을 이긴다. `index.html`에 SDK `<link>`를 다시 넣지 않는다.
