# AI 어항 — GM과 생활 세계 확장 계획

3.22.1 문맥 경계: 프로필의 출력·실제 문맥 설정을 따른다. 추가 출력 상한은 사용자가 명시한 경우만 보내고 알 수 없는 문맥은 가정하지 않는다. 새 호스트에서는 요청별 문자/바이트 제한을 두지 않으며, `measure`가 없는 이전 호스트만 기존 전송 범위를 호환한다. 큐·전체 본문·큰 결과 파일·네이티브 판단 및 번역 문맥은 호스트가 관리한다. 실제 문맥 초과 시 객체 단위 선택과 제한된 새-ID 재시도를 사용하고, 기억 실패는 원문을 보존하며 진행한다. 현재 계약은 README의 문맥 예산 절을 따른다.

3.21.1 안전 경계: 판단 요청은 호스트의 120초 상한을 따르고 실제 하루 분류별 호출 한도를 적용한다. 교류 요청은 만료·실패·취소로 종료할 수 있으며 자율 재시도 기록은 플레이어 명령의 보관 공간을 사용하지 않는다. 현재 요청 필드와 상태는 README의 서버 계약을 따른다.

3.21.2 서버 보강: 모델 슬롯이 차도 규칙 생활은 진행하고 기억 정체 중에는 식사·휴식을 우선한다. 원정 출발·계속/귀환 판단은 combat 예산으로 분리한다. 실제 요청 시도별 비용 집계에서 busy/빈 판단은 제외하고, 물품 ID 누락은 골드 이전으로 해석하지 않는다.

이 문서는 GM·생활 세계 확장의 구현 범위와 사용자 확정 정책을 담는다. 1~6절은 기존 생활 세계 확장 계획이며 현재 구현 명세가 아니다. 추가 작업인 **생활·자료 조사·토론 공간 확장**은 7절을 따른다. 반영된 기능의 사용법·운영 한도·저장 및 재시도 경계는 [사용 안내](README.md), 버전별 변경은 [변경 기록](CHANGELOG.md)을 따른다.

## 1. 완성 목표

DM을 GM으로 바꾸되 기존 세계 설정·대화·기억·던전 운영·외형 묘사 역할을 모두 유지한다. GM은 마을과 시설의 확장, 생활 사건, 건설 심사를 맡는다. AI 주민은 생활과 소비의 주체가 되고, 프로필이나 LLM 없이 움직이는 NPC가 거래·생산·공사를 수행한다.

주민의 필요가 수입·거래·건설 요청으로 이어지고, 완성된 시설이 지도·서비스·경제를 실제로 바꾸는 순환을 만든다. 건물과 아이템은 설명만 생성되는 것이 아니라 서버가 검증하는 기능을 갖는다.

## 2. 현재 구현과 재사용 지점

| 영역 | 확인된 현재 상태 | 변경 방향 |
| --- | --- | --- |
| DM | 세계 설정, 변경 제안, 분리된 기억, 던전 확장, 그림 외형 묘사 | 기존 역할을 보존하고 GM으로 통합 |
| 마을 | 공유 상수 지도·건물과 Canvas 도형 렌더링 | 세이브별 지도·시설 상태와 생성 이미지 렌더링 |
| 경제 | 골드, 장비·물약 상점, 자동 보급·판매, 의뢰 보상 | 같은 통화를 사용해 거래·재고·예치금 확장 |
| 아이템 | 장비 중심 인벤토리·평가·자동 판매 | 생활 물품을 지원하는 분류·수량·기능 계약 |
| NPC | 초대한 프로필과 연결된 주민·직업 | 기존 주민과 공존하는 규칙 기반 NPC |
| 이미지 | 게임 그림 큐, 생성 상태 추적, 라이브러리 해시, 생성 한도 | 건물·생활 아이템을 기존 파이프라인에 추가 |
| 진행 | 일부 생활·게임 그림 처리가 던전 진행에 종속 | 마을 진행과 던전 진행을 분리 |

주요 구현 위치는 `server/village/setup.mjs`, `server/rpg/rules.mjs`, `server/rpg/rpg.mjs`, `shared/rpg-systems.mjs`, `shared/tiles.mjs`, `server/rpg/game-art.mjs`, `page/village/map-paint.js`다. 모두 이 문서가 있는 플러그인 디렉터리 기준이다.

## 3. 책임과 데이터 경계

- GM: 세계관에 맞는 내용·외형을 제안하고 건설을 심사한다. 임의 코드·계산식·무제한 보상을 실행할 수 없다.
- AI 주민: 필요와 선호에 따라 행동을 요청한다. 구매·사용·제작·건설 요청은 구조화된 입력으로 서버에 전달한다.
- 규칙 기반 NPC: 프로필과 주민 기억 없이 일정·재고·직업 규칙에 따라 행동한다. 기존 AI 주민 직업을 일괄 대체하지 않는다.
- 서버: 돈·물품·부지·권한·진행 상태를 검증하고 한 번만 처리한다. GM 승인과 호스트의 실행·비용 권한은 별개다.
- 화면·어시스턴트·MCP: 같은 도메인 처리와 검증을 사용한다. 화면만 만들고 AI 주민이 사용할 수 없는 상태는 완료로 보지 않는다.

시설은 안정된 ID, 위치·점유 영역, 출입구, 기능, 소유 관계, 단계, 설계 리비전, 이미지 참조를 가진다. 그림이 아니라 시설 데이터가 충돌과 서비스를 결정한다.

아이템은 정의와 소유 수량·개별 인스턴스를 구분한다. 기존 장비 인스턴스 ID와 장착 참조를 유지하면서 중첩 가능한 생활 물품을 추가한다. 분류와 실제 사용 기능은 분리하고, 필요한 속성만 붙인다.

## 4. 단계별 구현과 완료 기준

### 1단계 — GM 통합과 세이브 기반 정비

- 화면·안내·프롬프트의 DM을 GM으로 바꾸고 기존 역할·기억·설정을 유지한다.
- 저장 키와 요청 ID는 호환성이 필요한 곳에 남기고, 내부 식별자를 무조건 일괄 치환하지 않는다.
- 새 데이터에 버전 마이그레이션을 추가하고 슬롯 전환·복사·초기화에 연결한다.
- 던전을 꺼도 생활과 게임 그림 처리가 진행될 수 있도록 실행 경계를 분리한다.

완료 기준: 기존 세이브의 골드·장비·의뢰·던전·GM 기억이 유지되고, 던전 비활성 상태에서도 마을 기능이 동작한다.

### 2단계 — 생활 아이템과 경제 공통 처리

- 장비 외에 음식, 재료, 건축 자재, 도구, 가구·장식, 생산품, 의뢰용 물품을 지원한다.
- 구매·판매·이전·소비·보관에 공통 수량·잔액·재고 검증을 적용한다.
- 서버가 지원하는 기능으로 섭취, 장착, 재료 투입, 도구 조건, 설치, 의뢰 납품을 표현한다.
- 장비 평가·중복 판매·보관함 정리에서 비장비 아이템을 명시적으로 분리한다.
- GM은 제한된 스키마 안에서 이름·설명·외형·기능을 제안한다. 사용자가 필요 상태 도입을 확정했으므로 3.21부터 배고픔·피로·기분·사교 만족을 주민별로 저장하고 음식·휴식·교류의 실제 효과에 연결한다. 정의는 슬롯 공용이며 GM과 사용자가 확장한다. 배고픔만으로 사망시키는 생존 규칙은 추가하지 않는다.

완료 기준: 생활 물품이 구매·보관·소비·납품되고, 재료가 장비처럼 자동 판매되지 않으며, 거래 재시도로 돈이나 수량이 복제되지 않는다.

### 3단계 — 세이브별 지도와 시설

- 기존 건물을 안정된 ID를 가진 저장 데이터로 옮기되 초기 외형과 기능을 보존한다.
- 서버 이동·충돌·장소 판정과 화면 배치가 같은 지도 상태를 읽게 한다.
- 부지 중복, 지도 경계, 출입구 접근과 주요 이동로를 검사한다.
- 시설 추가·증축뿐 아니라 마을 영역 확장도 지원한다. 초기 구현은 인접 구역을 제한된 단위로 개방하는 방식을 권장하며 무한 지형 생성은 포함하지 않는다.
- 지도 리비전이 바뀌면 이동 경로를 갱신하고, 영향을 받는 주민·NPC 위치를 안전하게 처리한다.

완료 기준: 새 시설과 확장 구역이 해당 세이브에 저장되고, 화면과 서버의 이동 가능 영역이 일치하며, 기존 주민을 건물 안에 가두지 않는다.

### 4단계 — 규칙 기반 NPC와 생활 순환

- 상인·생산 담당·건설 담당 NPC를 프로필 없이 생성·저장·표시한다.
- 일정과 이동 규칙을 재사용하고, NPC를 프로필 기반 주민 동기화에 그대로 넣지 않는다.
- 상인은 자금·재고와 거래 규칙을 사용하고, 생산은 재료·도구 조건·소요 시간에 따라 진행한다.
- AI 주민은 같은 거래·시설 서비스를 이용하고, 필요하면 구매·납품·건설 요청을 한다.
- 초기 검증용 생활 순환은 자재 거래, 간단한 생산·소비, 시설 이용으로 제한한다. 복잡한 세금·대출·투기 시장은 추가하지 않는다.

완료 기준: LLM 호출 없이 NPC가 이동·영업·거래·생산하고, AI 주민과 NPC가 같은 경제 규칙을 사용한다.

### 5단계 — 건설·증축과 GM 심사

1. 주민이 시설 종류와 위치 또는 증축 대상을 요청한다.
2. 서버가 비용·자재·부지를 검사하고 견적을 확정한다.
3. 돈·자재를 예치하고 부지를 예약한다.
4. GM이 사유와 함께 승인하거나 거절한다.
5. 승인된 공사는 서버 시간·작업 규칙에 따라 진행한다.
6. 완공 시 시설 기능을 활성화하고 예치금·자재를 한 번만 정산한다.

- 거절·취소·실패는 환불과 부지 예약 해제 상태를 명확하게 가진다.
- 승인 중복, 동시 부지 신청, 재시작 후 공사 재개를 처리한다.
- GM이 없거나 응답에 실패하면 요청을 보류하고, 임의 승인하거나 예치금을 소실시키지 않는다.
- 시설 확장과 지역 확장 모두 GM의 구조화된 변경 제안·실행 결과에 포함한다.

완료 기준: 요청부터 완공·서비스 이용까지 실제로 연결되고, 중복 결제·중복 완공·환불 중복이 없으며, 거절된 부지는 다시 사용할 수 있다.

### 6단계 — GM 생성 이미지와 통합 화면

- 기존 게임 그림 큐에 건물과 생활 아이템을 추가한다.
- GM이 세계관과 용도에 맞는 외형을 작성하고, 생성 설정에 따라 이미지를 만든다.
- 건물은 공통 화풍·시점·배치 기준을 적용하고, 지도상의 실제 시설 위치에 렌더링한다.
- 생성 결과를 세이브·대상 ID·설계 리비전에 연결한다. 증축 전 이미지가 늦게 도착해 새 외형을 덮어쓰지 않게 한다.
- 생성 중·실패·비활성 상태에서는 기존 그림이나 도형 표시를 유지한다. 성공 전에는 생성 외형 적용 완료로 표시하지 않는다.
- 일일 한도·큐 제한·재시도 제어를 재사용한다. NovelAI는 요청마다 `n_samples: 1`을 유지한다.
- GM 창, 시설 상세, 건설 요청·공사 상태, NPC 거래, 생활 인벤토리를 연결한다. 각 단계에서 필요한 최소 UI와 AI 작업 경로는 함께 구현하고 이 단계에서 통합한다.

완료 기준: GM이 생성한 건물 그림이 앨범에만 남지 않고 지도에 나타나며, 증축·재접속 후에도 올바른 그림과 시설 기능이 유지된다.

## 5. 게임 정책

| 결정 | 권장 시작점 | 아직 확정하지 않은 부분 |
| --- | --- | --- |
| GM의 건설 권한 | 주민의 게임 내 건설은 요청대로 GM이 심사 | 호스트 권한·비용 제한은 별도로 유지 |
| 건설비와 환불 | 사용자 확정: 거절·착공 전 취소 전액 반환, 착공 후 미사용분만 반환 | 시공 NPC가 있으면 사용된 건설비를 지급하고, 없으면 시스템 비용으로 소모. 미사용 예치는 별도 보관 |
| 공사와 생활 시간 | 사용자 확정: 마을이 깨어 있을 때만 진행 | 화면 종료와 마을 수면은 구분하며 서버 중단 시간은 소급하지 않음 |
| NPC 경제 | 사용자 확정: 유한 재고·자금과 제한된 정기 보충 | 보충량·임금·가격·공사비 수치는 기존 규칙을 우선 활용 |
| 시설 소유권 | 사용자 확정: 개인·공공 구분 | 주민 자금으로 지으면 개인 소유·수입, 공동 자금으로 지으면 공공 소유·수입 |

시공 NPC가 없어도 건설할 수 있어야 한다. 비용 수취인과 지급 내역을 공사에 연결해 재시도·NPC 변경 때문에 이중 지급되지 않게 한다. 새 제품 정책이 필요한 경우 사용자에게 확인하며, 확정한 정책을 구현 편의 때문에 변경하지 않는다.

## 6. 검증과 전달

- 기존 세이브 마이그레이션, 슬롯 격리·초기화, GM 기억과 기존 던전 기능 보존.
- 거래·예치·환불·완공의 중복 요청 및 실패·재시작 시 무결성.
- 비장비 자동 판매 방지, 수량·잔액·재고 부족과 경계값 검증.
- 건물 중복 배치·접근 불가 차단, 지도 확장 후 이동·렌더링 일치.
- 던전 비활성 상태의 생활 진행, 프로필 없는 NPC 진행.
- 이미지 실패·한도·재시도·슬롯 전환·증축 후 오래된 결과 배제.
- UI·AI 주민 행동·페이지 어시스턴트·MCP가 같은 처리 결과를 조회하는지 확인.

기존 `local-plugins/tests/ai-aquarium*.test.ts`를 재사용하고, 중요한 데이터 무결성·호환성에 한해 영구 회귀를 추가한다. 패키지는 저장소 루트에서 `node scripts/build-plugin.mjs --local ai-aquarium`으로 검증한다. 설치·배포는 구현 완료와 구분하며 별도 요청 없이 실행하지 않는다.

구현은 위 순서로 통합한다. 아이템·경제와 지도 구조는 1단계 이후 독립적으로 작업할 수 있지만, 같은 저장 상태를 수정하는 부분은 담당자를 하나로 둔다. 마지막에 통합 검증과 독립 리뷰를 한 번 수행한다.

계획 작성 시에는 소스 변경이나 실행 검증을 수행하지 않았다. 이후 구현 결과와 실제 검증 여부는 대화에서 보고하며 계획의 완료 기준을 검증 결과로 간주하지 않는다.

## 7. 추가 계획 — 생활·자료 조사·토론 공간

계획일: 2026-10-21. 이 절은 구현 제안이며 기능 완료나 제품 정책 확정을 의미하지 않는다.

### 7.1 목표와 범위

AI 어항을 주민이 자유롭게 생활하면서 앱의 자료를 읽고, 서로 질문·검토·토론하며, 출처가 있는 결과를 만드는 공간으로 확장한다. 모든 대화를 업무로 바꾸지 않는다. 일상 잡담과 목적 있는 공동 활동이 함께 존재한다.

- 던전은 삭제하지 않고 선택 기능으로 보존한다. 생활 중심 화면에서는 전투 정보를 숨기되 기존 세이브의 던전·장비·진행 기록은 유지한다.
- 여관·신전으로 시작하는 마을, 기부·건설·이미지·NPC 경제는 유지한다. 지식 활동에 참여하기 위해 돈을 벌거나 시설을 먼저 지을 필요는 없다.
- GM은 주제·참여자·진행·종료를 조율한다. 주민의 합의를 사실 판정이나 독립 검증으로 바꾸지 않는다.
- 첫 구현은 사용자가 지정한 주제와 게시글·지식 자료를 대상으로 한다. 파일·미디어와 자율 주제 발굴은 후속 단계다.
- 앱의 기존 채팅 엔진·도구·게시판·지식·작업 상태를 재사용한다. 별도 검색 엔진, 벡터 저장소, 범용 에이전트 실행기를 만들지 않는다.
- 이번 범위에 외부 웹 자동 탐색, 무제한 자율 운영, 원본 자료 자동 수정·삭제, 자동 게시를 포함하지 않는다.

### 7.2 확인된 기반과 연결 과제

| 기반 | 현재 근거 | 필요한 연결 |
| --- | --- | --- |
| 던전 없는 생활 | `local-plugins/ai-aquarium/server/rpg/rpg.mjs`의 `tick`은 생활과 전투 진행을 분리 | 생활 중심 표시·설정, 던전 재활성화 호환성 |
| 주민 대화·기억 | `local-plugins/ai-aquarium/server/village/talk.mjs`는 `mode: 'text'`의 짧은 대화 사용 | 잡담과 조사·토론을 구분하고 실제 읽은 근거만 공유 |
| 도구를 사용하는 프로필 | `backend/src/services/plugins/pluginLlm.ts`와 `plugins/README.md`의 `mode: 'profile'` | 조사 작업을 기존 실행 경로에 연결하고 실제 도구 결과 추적 |
| 게시글·지식 | `backend/src/mcp/tools/postTools.ts`의 검색·열람 및 기존 게시판 서비스 | 허용된 자료 선택, 인용·버전 확인, 결과 초안 |
| 화면 없는 실행 | 플러그인 서버, 기존 작업 ID·취소·권한 검사 | 마을/슬롯과 작업 연결, 중단·재시작 후 안전한 상태 확인 |

단순히 대화의 mode만 바꾸면 안 된다. `profile` 모드는 기존 자동화 채팅방·도구·검토 카드를 사용하며 `structuredOutput`을 허용하지 않는다. 일상 대화는 현재의 구조화된 text 경로를 유지하고 조사만 profile 경로로 실행한다. 조사 결과의 성공 여부는 모델의 문장이 아니라 `profileRun`의 실제 도구 상태와 산출물 참조로 판정한다.

같은 플러그인·계정·프로필은 호스트의 자동화 채팅방을 공유한다. 슬롯마다 별도 방이 생긴다고 가정하지 않는다. 엄격한 슬롯 문맥 격리와 작업별 읽기 전용 제한이 현재 계약으로 가능한지 1단계에서 확인하며, 불가능하면 프롬프트만으로 보장하지 않고 필요한 최소 공용 연결을 먼저 정의한다.

### 7.3 실행·데이터 계약

- 공동 활동은 목표, 자료 범위, 참여 주민, 진행 상태, 실행 예산, 실제 작업 참조, 결과 참조를 가진다. 기존 작업 기록에 재사용할 계약이 있으면 그것을 먼저 사용하고 어항에는 연결에 필요한 상태만 둔다.
- 상태는 준비·조사·토론·정리·완료 외에 일시정지·승인 대기·실패·취소를 구분한다. 근거가 부족한 결과도 그렇게 표시하고 완료와 검증됨을 구분한다.
- 자료 참조에는 종류·ID·가능한 리비전/버전·읽은 구간·짧은 발췌를 보존한다. 원문 전체나 모든 도구 응답을 어항 DB에 복제하지 않는다.
- 실제 조사한 주민과 공유받은 주민을 구분한다. 공동 활동에 참가하지 않은 주민에게 전체 자료·개인 기억을 자동 전파하지 않는다.
- 출력은 요약, 근거, 상충하는 주장, 합의되지 않은 점, 다음 질문으로 구성한다. 출처 변경·삭제·접근 거절 시 해당 근거를 다시 확인할 필요가 있음을 표시한다.
- 게시글 본문과 도구 응답은 참고 자료다. 그 안의 지시문으로 활동 범위·권한·예산을 바꾸지 않는다.
- 모든 실행은 계정·마을·슬롯 세대·활동·단계·요청 ID와 연결한다. 재시도는 동일 ID로 상태를 조회하고, 늦은 결과가 다른 슬롯이나 초기화된 마을에 적용되지 않게 한다.
- 백그라운드 실행 계정과 자료 접근 권한을 검증한다. 프로필이 해당 자료를 읽을 수 있다는 사실을 모든 주민·모든 계정의 공유 허가로 해석하지 않는다.

### 7.4 단계별 구현과 완료 기준

#### 1단계 — 생활 중심 설정과 안전한 조사 계약

- 던전 설정은 유지하면서 생활 중심 화면의 표시 범위를 분리한다. 기존 세이브에는 새 활동을 자동 시작하지 않는다.
- 게시판의 선택 카테고리 또는 명시한 게시글을 첫 자료 범위로 삼는다. 허용 범위 밖의 검색·열람을 실행단에서 제한할 수 있는지 확인한다.
- 기존 profile 실행의 도구 제한, 자동화 채팅방 공유, 계정 권한, 검토·취소·비용 계측을 점검한다.
- 슬롯 문맥 격리, 읽기 전용 도구 제한, 실행 한도에 공용 계약이 부족하면 해당 연결만 최소 확장한다. 공용 변경은 제작 가이드·SDK 계약·공용 회귀에도 반영한다.
- 단계·활동별 호출 상한과 동시 실행 1개를 서버에서 검사한다. 토큰·사용량의 실제 계측 범위를 확인하고, 보장할 수 없는 금액 상한을 표시하지 않는다.

완료 기준: 던전 없이 기존 생활이 유지되고, 지정 범위 밖 조회·변경 도구 실행과 다른 슬롯의 문맥 재사용을 차단하는 경로가 검증된다. 이 조건이 충족되기 전에는 자율 조사 기능을 켜지 않는다.

#### 2단계 — 사용자가 시작하는 자료 조사

- 사용자가 주제·자료 범위·참여 주민을 고르고 조사 활동을 시작·중단할 수 있게 한다.
- GM은 필요한 질문과 역할을 제안하되 범위·권한·예산을 늘리지 않는다. GM 프로필이 없어도 사용자가 지정한 활동은 진행할 수 있게 한다.
- 조사 주민은 실제 검색·열람 도구를 사용한다. 검색 요약만 본 경우 원문을 읽었다고 기록하지 않는다.
- 작업 큐·상태·오류·취소를 기존 호스트 실행에 연결하고, 서버 재시작 후 먼저 기존 작업을 조회한다.

완료 기준: 앱에 존재하는 자료에서 실제 근거가 수집되고, 화면에서 출처를 열 수 있으며, 자료가 없거나 접근할 수 없으면 그 상태가 명확히 표시된다.

#### 3단계 — 근거를 공유하는 주민 토론

- 조사·검토·정리 역할을 활동별로 배정한다. 주민의 성격과 관심사는 표현·관점에 반영하되 사실 근거를 대신하지 않는다.
- 참여자는 공유된 근거와 질문을 바탕으로 발언한다. 짧은 말풍선과 상세 토론 기록을 분리한다.
- 검토자는 원문과 주장 일치 여부, 누락·모순·반례를 확인한다. 같은 모델끼리 동의했다는 이유로 독립 검증 배지를 붙이지 않는다.
- 설정한 회차에 도달하거나 새 근거가 없으면 정리한다. 추가 조사가 필요하면 남은 예산 안에서만 실행한다.
- 일상 대화와 공동 활동이 같은 주민을 동시에 점유하지 않도록 조정하고, 활동 종료 후 기존 생활로 복귀시킨다.

완료 기준: 최소 두 주민이 서로의 근거를 참조하며 토론하고, 주장·출처·의견 차이를 추적할 수 있다. 반복 발언으로 끝없이 호출하지 않는다.

#### 4단계 — 결과 초안과 통합 화면

- 기존 게시글/지식 저장 계약으로 결과 초안을 만든다. 검토·저장 경로가 지원하는 승인 정책을 그대로 사용하고 자동 게시하지 않는다.
- 어항에는 현재 활동·담당 주민·진행 상태·출처·결과 링크를 표시한다. 원본 상세와 전체 도구 기록은 기존 앱 화면으로 연결한다.
- 자료 권한이 다른 사용자에게 결과·발췌가 노출되지 않도록 초안과 참조의 접근 범위를 검사한다.
- 페이지 어시스턴트는 주제·자료·참여자 초안과 상태 조회를 지원하고, 비용이 발생하는 시작·변경은 기존 검토 경로를 따른다. 화면·MCP·서버가 같은 검증을 사용한다.
- 저장 재시도로 중복 글이 생기지 않게 한다. 논의의 결론은 우선 미검증 결과이며, 지식의 검증 상태를 임의 승격하지 않는다.

완료 기준: 시작부터 자료 조회·토론·출처가 있는 초안까지 이어지고, 취소·실패·재시도·승인 대기 상태가 화면과 실제 실행에서 일치한다.

#### 5단계 — 파일·미디어와 선택적 자율 활동

- 1~4단계 검증 후 파일·연결 프로젝트·미디어를 각 도구의 실제 지원 형식과 읽기 범위에 맞춰 확장한다. 메타데이터 조회와 원본 내용 이해를 구분한다.
- 사용자가 켠 경우에만 새 자료나 이전 활동의 미해결 질문으로 주제를 제안한다. 변경 알림과 자료 버전을 활용하고 전체 자료를 주기적으로 재검색하지 않는다.
- 같은 자료·주제·버전의 중복 활동을 막고, 새 근거가 없으면 쉬게 한다.
- 도서관·토론 장소는 선택적 생활 표현으로 연결한다. 필수 기능을 시설 구매 뒤에 숨기거나 지식 활동을 기부 보상과 결합하지 않는다.

완료 기준: 허용한 새 자료에만 제한적으로 반응하고, 변경 없는 자료를 반복 조사하지 않으며, 자율 활동을 끄면 신규 실행이 시작되지 않는다.

### 7.5 첫 배포 범위와 제안 기본값

첫 배포는 1~4단계로 제한한다. 아래 값은 사용자 확정 정책이 아니라 구현 시작점이며 실제 모델과 비용을 보고 조정한다.

- 신규 마을의 생활 중심 선택을 제공하되 기존 마을의 던전 설정은 자동 변경하지 않는다.
- 사용자 지정 주제만 실행하고 자율 주제 발굴은 기본 꺼짐으로 둔다.
- 활동당 주민 2~3명, 토론 최대 3회차, 마을당 동시 조사 실행 1개를 시작점으로 한다.
- 검색·열람 수와 모델 호출 상한을 시작 전에 표시하고, 재시도도 예산에 포함한다. 실제 집행 가능한 상한 수치는 1단계의 호스트 계약 확인 후 확정한다.
- 저장은 기존 승인 경로의 결과 초안까지만 지원한다. 자동 게시·원본 수정은 허용하지 않는다.
- 수면·일시정지는 신규 실행을 막고, 진행 중 요청은 기존 취소/결과 회수 계약으로 정리한다. 오프라인 경과 시간을 소급해 조사하지 않는다.

### 7.6 검증·작업 분담·전달

- 기존 어항 테스트에 던전 비활성 생활, 기존 세이브 보존, 슬롯 전환·복사·초기화 격리를 추가 검증한다.
- 중요한 영구 회귀: 자료 범위·계정 권한·읽기 전용 제한, 실제 도구 실패, 늦은 결과, 중복 시작·저장, 취소·재시작, 사용량 상한, 검토 대기.
- 출처의 ID·버전·발췌와 실제 원문을 대조한다. 봇이 조회했다고 말하는 문장 자체를 성공 판정에 사용하지 않는다.
- 화면에서는 주제 작성·자료 선택·시작·상태 확인·중단·결과 초안 열기를 실제 브라우저로 검증한다. 초기·빈 결과·진행·실패·승인 대기 상태와 작은 화면을 포함한다.
- 파일 소유권은 실행·저장 담당, 화면 담당으로 구분한다. 공용 계약이 먼저 확정되어야 화면과 서버를 독립 구현할 수 있다. 동일 저장 파일은 한 담당자가 소유한다.
- 최종 통합 테스트와 ZIP 빌드 후 독립 리뷰를 한 번 수행한다. 실제 모델·실제 자료 접근·과금 검증은 승인된 자료와 예산으로 별도 실행하고, 자동 테스트와 구분해 보고한다.
- 설치·배포·실제 이미지 생성은 이 계획에 포함하지 않는다. 이번 계획 작성에서는 게임 코드 수정이나 기능 실행 검증을 하지 않는다.
