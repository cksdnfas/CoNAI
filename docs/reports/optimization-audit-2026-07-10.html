한눈에 보는 결론

가장 먼저 손댈 곳: 프런트 수동 청크 경계와 대용량 ZIP 생성 경로다. 둘 다 코드 구조 문제가 아니라 실제 초기 전송량·메모리·DB 호출 수에 직접 영향을 준다.
  1. 초기 로드: 지연 로딩 대상인 Konva와 이미지 목록 벤더가 초기 정적 의존성에 포함된다. 초기 JS는 약 1.30MB raw / 342.45KB gzip이다.
  2. 대량 다운로드: 최대 200개 파일을 해시별 DB 조회 후 AdmZip.toBuffer()로 한 번에 메모리에 만든다. 생성 이력 경로는 그 전에 최대 500건을 다시 개별 조회한다.
  3. DB 탐색: 기본 홈 피드는 커서 페이지네이션이 적용됐지만 복합 검색·그룹 피드는 여전히 COUNT + OFFSET, 일부 미리보기는 ORDER BY RANDOM()이다.
  4. 미디어 CPU: FFmpeg 인코딩은 업로드·생성 결과·백업 가져오기에서 호출되지만 전역 동시성 제한이 없다.
  5. 관측성: 캐시 통계는 있으나 라우트 p95, SQL 시간/호출 수, 이벤트 루프 지연, FFmpeg 대기열을 한 화면에서 판단할 성능 진단 기능이 없다.

우선순위별 최적화 제안

P0

수동 청크 경계를 고쳐 초기 로드에서 Konva·목록 벤더 분리

확신 높음

관찰: 초기 정적 JS 의존성은 12개, 1,301.98KB raw / 342.45KB gzip이다. 이 안에 konva 90.88KB gzip과 image-list-vendor 31.87KB gzip이 포함된다. 이미지 편집 모달과 목록은 lazy지만 엔트리 청크가 이 벤더들을 정적으로 import한다.

원인 후보: frontend/vite.config.ts:27-52의 manualChunks가 feature vendor를 강제 소유하면서 React 공유 의존성이 해당 청크로 빨려 들어간 구조다. 실제 빌드 엔트리는 konva-*.js와 image-list-vendor-*.js를 정적 import한다.

권장: React/ReactDOM을 먼저 명시적 react-vendor로 고정하고 feature vendor는 lazy route가 소유하게 재구성한다. 대안으로 Konva 수동 청크 규칙을 제거하고 Rolldown 자동 분할을 비교한다. 목표는 초기 JS 250KB gzip 이하, 로그인/비편집 화면에서 Konva 네트워크 요청 0회다.

P0

대용량 ZIP을 벌크 조회 + 스트리밍 방식으로 전환

확신 높음

관찰: backend/src/routes/images/query-file-helpers.ts:243-297은 최대 200개 해시를 순회하며 메타데이터와 활성 파일을 각각 조회하고, statSync 후 AdmZip.toBuffer()로 결과 전체를 메모리에 만든다. 허용 원본 합계는 512MiB다.

추가 병목: 생성 이력 다운로드는 mediaRouteHandlers.ts:25-44에서 최대 500개 이력 ID를 findByIdWithMetadata로 개별 조회한 뒤 같은 ZIP 경로로 들어간다. 최악의 경우 수백 회 DB 왕복과 큰 메모리 피크가 겹친다.

권장: 이미 존재하는 MediaMetadataModel.findByHashesWithFiles()를 재사용하고 생성 이력 벌크 조회 API를 추가한다. ZIP은 응답 스트림 또는 임시 파일로 backpressure를 적용한다. 100개 파일 기준 DB 쿼리 3회 이하, ZIP 생성 중 추가 RSS 128MB 이하를 완료 기준으로 둔다.

P0

성능 진단 모드를 제품 기능으로 추가

효과 측정 기반

현재 기반: /api/system/cache-stats와 큐 상태·진행률은 이미 있다. 반면 라우트/SQL/이벤트 루프/메모리/FFmpeg를 묶은 지표는 없다.

권장 기능: 관리자 전용 “성능 진단” 화면에 최근 5분 라우트 p50/p95/p99, 요청당 SQL 수·총 시간, 느린 SQL 샘플과 EXPLAIN QUERY PLAN, 이벤트 루프 지연, RSS/힙, 캐시 hit rate, FFmpeg 대기/실행 수를 표시한다. 개인정보·프롬프트·파일 경로는 기록하지 않는다. 이후 최적화는 이 지표로 전후 비교한다.

P1

번역 카탈로그를 기능·언어 단위로 지연 로딩

확신 높음

관찰: frontend/src/i18n/resources/index.ts:52-67은 모든 기능 카탈로그를 하나로 합치고 i18n/index.tsx:22가 이를 기본값으로 즉시 import한다. 번역 소스만 약 470KB이며, image-generation.ts 145.8KB, module-graph.ts 111.8KB, settings.ts 63.4KB다. 결과적으로 utils 청크가 89.10KB gzip으로 초기 로드된다.

권장: shell/auth만 bootstrap catalog로 유지하고 route 진입 시 feature catalog를 등록한다. 가능하면 현재 선택 언어만 로드한다. 번역 키 누락 검증은 빌드 시 유지해 런타임 fallback에 숨지 않게 한다.

P1

복합 검색·그룹 피드를 커서 페이지네이션으로 확대

확신 높음

잘된 부분: 기본 홈 피드는 이미 first_seen_date + composite_hash 커서를 사용하고 다음 페이지에서 total 계산을 생략한다.

남은 부분: ImageSearchModel.ts:104-150, 259-301은 복합/자동태그 검색에 COUNT(DISTINCT ...)와 LIMIT/OFFSET을 사용한다. 그룹 infinite query도 page 번호 기반이다.

권장: 정렬별 안정적인 복합 커서(sortValue + composite_hash)를 정의하고 total은 첫 페이지 선택 옵션 또는 짧은 TTL 캐시로 제한한다. 깊은 스크롤의 응답 시간이 페이지 번호에 비례해 늘지 않는 것을 계약 테스트로 고정한다.

P1

FFmpeg 인코더에 전역 동시성 제한과 작업 큐 적용

확신 높음

관찰: videoOptimizationService.ts:78-158은 호출마다 FFmpeg 프로세스를 spawn한다. 업로드, 생성 결과, 백업 가져오기가 모두 이 경로를 await하지만 전역 semaphore가 없다.

권장: CPU/디스크 성능에 따라 기본 1~2개의 encoder slot을 두고 대기열·취소·진행률을 노출한다. 직접 업로드는 호환성이 허용되면 202 작업 방식으로 전환하고, 그렇지 않으면 동시성 제한만 우선 적용한다. 이 기능은 과부하 시 API 전체가 느려지는 것을 막는다.

P1

그룹·자동폴더 미리보기의 ORDER BY RANDOM 제거

확신 높음

관찰: 기본 랜덤 미디어는 이미 indexed id seek 방식으로 최적화됐고 계약 검증도 통과한다. 그러나 GroupImageQueries.ts:192,215, AutoFolderGroup.ts:270,334, danbooruBrowserService.ts:479에는 전체 후보 정렬형 ORDER BY RANDOM()이 남아 있다.

권장: 그룹별 최소/최대 membership id 또는 random pivot + wraparound를 사용한다. 여러 미리보기는 bounded sample 또는 미리 계산된 preview pool로 바꾼다. 기존 랜덤 선택 계약을 그룹·자동폴더까지 확장한다.

P2

배치 썸네일 조회의 N+1과 동기 파일 확인 제거

query-list-helpers.ts:175-223은 최대 100개 해시를 순회하며 해시별 메타데이터/파일 조회와 existsSync를 수행한다. 벌크 DB 조회로 합치고, 썸네일 존재 상태는 파일 검증 서비스가 관리하는 DB 상태 또는 짧은 TTL 캐시로 대체한다.

P2

월페이퍼 browse-content 폴링 통합

wallpaper-widget-data.ts:30-35은 동일 API를 scope + refreshInterval별 query key로 나눠 폴링한다. 큐 상태·최근 결과·활동 위젯이 같은 payload를 별도 요청할 수 있다. 하나의 공유 query key와 최소 활성 주기 스케줄러를 사용하고 각 위젯은 select로 필요한 데이터만 구독한다.

P2

NAI 자산 저장소의 동기 디스크 스캔을 인덱스화

naiAssetStore.ts는 목록/탐색/삭제에서 동기 readdirSync/readFileSync/existsSync/writeFileSync를 반복하고 일부 조회 중 파일·썸네일 보정도 수행한다. 메타데이터 index를 메모리/SQLite에 유지하고 자산 hydration은 백그라운드로 분리하면 자산 수 증가 시 API 지연과 이벤트 루프 정지를 줄일 수 있다.

P2

React Compiler 빌드 비용을 별도 계측

현재 빌드는 @rolldown/plugin-babel 타이밍 경고를 낸다. React Compiler를 무조건 제거하지 말고, 전체 적용/고비용 디렉터리 제외/비활성 3개 빌드의 시간과 런타임 React Profiler 결과를 비교한다. 런타임 이득이 없는 영역은 제외해 프런트 빌드 20초 이하를 목표로 한다.

이미 잘 되어 있어 재작업하지 않을 부분

  • 홈 이미지 피드의 커서 페이지네이션과 다음 페이지 total 생략
  • Virtuoso 기반 이미지 그리드/매슨리 가상화와 memoized context
  • generation queue의 SQL 필터, recent-completed index, payload pruning, ETA 경량 샘플
  • SQLite WAL, synchronous=NORMAL, busy timeout과 그룹 set-based write
  • 갤러리 캐시 무효화 디바운스와 캐시 통계 API
  • 기본 랜덤 이미지 선택의 indexed id seek
  • 이미지 편집기·페이지·대형 패널의 route/component lazy loading 자체
  • 비디오 H.264 MP4 최적화 및 실패/비효율 인코딩 fallback

주의점

  • 이번 점검은 정적 소스·프로덕션 빌드·계약 검증 기반이다. 실제 운영 데이터 규모와 동시 사용자 부하를 재현한 벤치마크는 아직 없다.
  • 따라서 검색 p95나 FFmpeg 처리량의 절대 수치는 성능 진단 계측을 먼저 넣은 뒤 확정해야 한다.
  • Graphify의 일반 자연어 질의는 키워드 매칭 노이즈가 있어, 그래프는 구조 탐색에만 사용하고 모든 핵심 판단은 최신 소스와 빌드 결과로 다시 확인했다.
  • 코드는 변경하지 않았으며 이 HTML 보고서만 추가했다.
