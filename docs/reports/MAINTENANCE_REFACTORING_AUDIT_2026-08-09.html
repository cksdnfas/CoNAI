3. BackgroundProcessorService를 단계형 파이프라인으로 분리

backend/src/services/backgroundProcessorService.ts는 1,013줄이고 DB, sharp, p-limit, 해시, 동영상, 썸네일, 자동 분류, 자동 태그, 워처, 유지보수 잠금, 가시성, 캐시, WAL을 한 서비스에서 조정한다.

권장 변경 단위

  1. 먼저 현재 public 메서드와 DB 상태 전이를 그대로 둔 채 이미지/동영상 processor를 별도 모듈로 이동한다.
  2. 후처리 단계가 { stage, status, retryable, error }처럼 명시적 결과를 반환하게 해 실패 위치를 남긴다.
  3. 배치 서비스는 동시성, 중지, 잠금, 재예약만 책임지게 한다.
  4. 자동 분류·그룹 할당·자동 태그는 해시 저장 성공 뒤 호출되는 후처리 단계로 유지하되, 한 단계 실패가 이전 성공을 되돌리지 않도록 현재 멱등성을 보존한다.

  • 권한·데이터 무결성·마이그레이션·큐 상태 전이는 실제 함수와 임시 DB 기반 검증을 우선한다.

  • 새 리팩터링 때는 해당 영역의 기존 verify script를 동작 검증과 구조 검증으로 나누어 함께 이동한다.

6. 낮은 우선순위 정리 후보

내장 시스템 모듈 정의 레지스트리

backend/src/database/userSettingsBuiltinModuleDefinitionData.ts는 2,330줄의 단일 배열에 37개 정의·10개 카테고리를 담고 있다. 런타임 복잡도보다 변경 충돌과 리뷰 비용이 문제다.

카테고리별 파일로 나누고 현재 순서를 유지하는 aggregator에서 합치면 된다. operation key, legacy name, 기본값 검증은 기존 verifyBuiltinSystemModuleDefinitions.ts를 그대로 사용한다.

백엔드 시작·종료 수명주기

backend/src/index.ts는 811줄·37개 import이고 startServer()가 약 506줄이다. 라우트와 런타임 부수효과는 이미 일부 helper로 분리돼 있어 방향은 좋다.

다음 정리는 startServer() 전체 재작성보다 619-777줄의 graceful shutdown coordinator와 middleware/bootstrap 조립을 분리하는 정도가 적절하다. 종료 순서는 파일 워처 → 스케줄러 → 임시 파일 → daemon → DB 순서를 그대로 보존해야 한다.

지금 손대지 않아도 되는 부분

  • 번역 리소스 대형 파일: image-generation.ts, module-graph.ts, settings.ts는 크지만 정적 사전 성격이 강해 크기만으로 분리할 이유가 약하다.
  • Graphify 순환 참조: 현재 검출된 3파일 순환은 핵심 두 연결이 type-only다. 즉시 장애 수정 대상이 아니라 히스토리 타입 이동 때 자연스럽게 제거하면 된다.
  • TODO 청산 작업: 제품 소스에서 TODO/FIXME/HACK 주석은 확인되지 않았고 빈 catch 블록도 없었다.
  • 무차별 any 제거: 119개 파일에 any 사용이 있으나 ComfyUI·메타데이터·SQLite 동적 row 같은 외부 경계가 많다. 경계 스키마를 손보는 작업과 함께 좁혀야 하며 숫자만 줄이는 전역 치환은 권장하지 않는다.

해당 영역 검증을 함께 이동
기존 verify를 버리지 말고 동작 검증과 구조 검증을 분리해 리팩터링 경계에 맞춘다.

완료 기준

  • 설정 API wire contract가 한 소스에서 나오고 프런트·백엔드 로컬 타입은 UI/런타임 전용만 남는다.
  • 생성 히스토리 필터 SQL이 한 빌더를 사용하며 쓰기 순서와 이벤트·보존 호출이 한 서비스에 모인다.
  • 백그라운드 미디어 배치 서비스가 동시성·중지·재예약만 담당하고 이미지/동영상 처리 단계는 독립 검증 가능하다.
  • module graph node card에 새 operation key를 추가할 때 본체 조건 체인을 수정하지 않아도 된다.
  • 고위험 계약은 실제 함수/DB 기반 검증으로 보호되고, 정적 소스 검사는 구조 금지 규칙에 집중한다.
  • 각 단계는 독립 커밋과 기존 영역별 검증을 통과한 뒤 다음 단계로 넘어간다.

이 문서는 현재 코드의 유지보수 위험 조사 결과다. 구현 계획의 승인이나 코드 변경을 포함하지 않는다.
