ComfyUI 실시간 진행률 수집 적용성

평균 실행시간 기반 진행률을 실제 노드·샘플링 스텝 이벤트로 대체할 수 있는지 조사

조사일 2026-08-07

결론

적용 가능 — Go. 표준 ComfyUI 서버는 /ws WebSocket으로 현재 노드, KSampler 스텝, 성공·오류·중단, 큐 변화를 실시간 전송한다. CoNAI의 실행 중 퍼센트는 기존 시간 추정값보다 훨씬 정확한 progress.value / progress.max로 교체할 수 있다.
실측 가능 현재 노드와 표준 KSampler의 현재/전체 스텝
추정 유지 아직 시작하지 않은 큐 작업의 남은 시간
부분 지원 모든 커스텀 노드를 합친 워크플로 전체 퍼센트

핵심 구분: “현재 실행 중인 샘플러의 진척도”는 실측할 수 있지만, “미래 큐 대기시간”과 “진행 훅이 없는 모든 노드까지 포함한 절대적인 전체 퍼센트”는 ComfyUI가 직접 제공하지 않는다.

현재 CoNAI에서 오차가 생기는 이유

실행시간 기준값

최근 완료 작업을 최대 12건씩 모아 중앙값을 사용한다. 우선순위는 워크플로+서버 → 워크플로 → 서버 → 전체 ComfyUI 순이다.

backend/src/routes/generation-queue/queue-eta.ts:104, 114-205

화면 진행률

경과시간 / 중앙값 실행시간을 퍼센트로 만들고 완료 전에는 최대 99%로 제한한다. 모델 로딩, 해상도, 스텝 수, 캐시 상태가 달라지면 오차가 커진다.

frontend/src/features/image-generation/components/generation-queue-ui.ts:315-332

완료 감지 방식

현재는 /history/{prompt_id}를 기본 2초 간격으로 폴링해 완료·오류만 확인한다. 중간 노드나 샘플링 스텝은 받지 않는다.

backend/src/services/comfyuiService.ts:291-395

이미 준비된 연결점

ComfyUI 요청에 client_id = conai-job-{queueJobId}를 이미 넣고 있고, CoNAI 백엔드→프론트엔드 SSE 런타임 이벤트도 존재한다. 새 진행률을 전달할 골격은 갖춰져 있다.

backend/src/services/comfyuiService.ts:241-269 · backend/src/services/runtime-events/runtimeEventPublishers.ts:71-87

판단: 현재 중앙값 계산이 잘못된 것은 아니다. 큐 대기시간·대체 표시용으로는 유효하지만, 실행 중인 ComfyUI 작업의 진행률 정본으로 사용하기에는 정보가 부족하다.

표준 KSampler는 내부적으로 ProgressBar(steps)를 만들고 매 콜백마다 update_absolute(step + 1, total_steps)를 호출한다. 서버는 이 값을 그대로 progress WebSocket 메시지로 전송한다. 즉, 20스텝이면 실제 1/20 … 20/20을 받을 수 있다.

구현 시 중요한 세부사항

1. 연결을 먼저 열고 제출

WebSocket이 열린 뒤 같은 client_id로 프롬프트를 제출해야 첫 이벤트를 놓치지 않는다. CoNAI의 기존 conai-job-{id} 값을 그대로 재사용할 수 있다.

2. 반드시 prompt_id로 필터링

서버별·잡별 이벤트가 섞일 수 있으므로 prompt_id가 현재 잡과 일치할 때만 반영한다. 재연결 직후 executing 메시지는 현재 소스에서 prompt_id가 없을 수 있어 단독 신뢰하면 안 된다.

3. executed를 노드 완료로 쓰지 않기

공식 문서상 executed는 UI 출력을 반환하는 노드에서만 온다. 현재 노드 전환은 executing, 전체 성공은 execution_success 또는 executing.node === null로 판단한다.

4. 이벤트 빈도 제한

ComfyUI 자체가 일반 진행 이벤트를 최소 100ms·0.5% 변화로 제한한다. CoNAI SSE는 250~500ms 단위로 최신값만 합쳐 보내면 다중 잡에서도 충분하다.

5. 커스텀 노드 한계

ProgressBar 훅을 호출하지 않는 커스텀 노드는 세부 퍼센트를 보내지 않는다. 이때는 현재 노드명과 기존 예상값을 함께 사용한다.

6. backend_type 범위

우선 backend_type = comfyui인 표준 직접 서버에 적용한다. 현재 별도 실행 경로인 modal은 같은 WebSocket 계약을 보장하지 않으므로 기존 방식 유지가 안전하다.

권장 도입 순서

  1. 수집: 표준 ComfyUI 서버에 잡별 WebSocket 모니터를 연결하고, 성공·오류 시 기존 /history 결과 수집으로 이어 붙인다.
  2. 전달: queue.job.progress를 기존 계정 제한 SSE에 추가하고, 최신 상태를 메모리 레지스트리로 유지한다.
  3. 표시: ComfyUI 실행 중에는 실측 스텝을 우선 표시하고, 미수신·연결 끊김일 때만 현재 중앙값 계산으로 폴백한다.
  4. 복구: WebSocket 재연결 시 같은 clientId를 사용하고 /queue·/history로 상태를 재동기화한다.
  5. 검증: 표준 KSampler 20스텝, 캐시 재사용, 2개 큐, 강제 연결 끊김, 오류·중단, 진행 훅 없는 커스텀 노드 케이스를 확인한다.
