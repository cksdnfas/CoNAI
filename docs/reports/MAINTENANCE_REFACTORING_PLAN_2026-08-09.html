유지보수·리팩터링 실행 계획서

2026-08-09 유지보수 조사 보고서에서 확인한 3개 고위험 영역(설정 계약, 생성 히스토리, 백그라운드 미디어 처리)과 2개 중간 위험 영역(UI hotspot, 검증 자산)을 한 번에 한 경계씩, 기존 계약을 유지한 채 이동하기 위한 커밋 단위 실행 계획이다.

작성일 2026-08-09 · 근거 MAINTENANCE_REFACTORING_AUDIT_2026-08-09.html · 브랜치 alphatest · 기준 커밋 bf5c4bc1

실행 원칙

  • 계약 불변: API wire 응답 형태, DB 스키마·상태 전이, SSE 이벤트 종류·발행 조건, 종료 순서를 바꾸지 않는다. 이 계획에는 마이그레이션이 없다.
  • 한 경계씩: Phase 1~4는 순차 진행하며, 세 고위험 영역을 동시에 열지 않는다. 한 Phase 안에서도 아래 커밋 단위를 넘어 합치지 않는다.
  • 독립 커밋: 각 커밋 단위는 단독으로 revert 가능해야 하고, 해당 영역 verify + 워크스페이스 타입 검사를 통과한 뒤에만 다음 단위로 넘어간다.
  • 검증 동반 이동 (Phase 5는 병행 트랙): 영역을 옮길 때 그 영역의 기존 verify 스크립트를 동작 검증과 구조 검증으로 나누어 함께 이동한다. 별도 테스트 플랫폼·harness는 도입하지 않는다.
  • 대규모 재작성 금지: 정규화·기본값·멱등성 등 현재 동작을 보존하는 추출만 한다. 파일이 크다는 이유만으로는 쪼개지 않는다.

Phase 1 — 설정 계약 단일화

같은 설정 계약이 세 파일(backend/src/types/settings.ts 363줄·62 export, frontend/src/types/settings.ts 325줄·57 export, shared/src/types/settings.ts 72줄·소비처 0)에 나뉘어 있고 54개 export 이름이 겹친다. shared를 유일한 wire contract 소스로 만들고, 프런트·백엔드 로컬 타입은 view model·서버 런타임 전용만 남긴다.

1-0드리프트 정본 판정 (코드 변경 없음, 판정 기록만)

이미 갈라진 3건의 정본을 실제 런타임 응답 기준으로 확정하고 결정을 커밋 메시지 또는 본 문서 갱신으로 남긴다. 판정 원칙: 응답을 생산하는 백엔드 런타임이 정본이며, 프런트에 없는 필드는 shared에 추가하는 방향으로 해소한다.

  • GeneralSettings.headerNavigation — shared는 선택, 백엔드는 필수. 실제 응답에 항상 포함되는지 확인 후 필수/선택 확정.
  • TaggerDependencyCheckResult — 백엔드의 상세 의존성 상태 필드를 shared 계약에 반영할지 확정.
  • wallpaper 타입 — 백엔드·프런트가 서로 다른 소스를 쓰므로 단일 소스 위치 확정.

1-1shared wire contract 재작성 — GeneralSettings 도메인

shared/src/types/settings.ts를 실제 API로 오가는 순수 계약으로 재작성한다. UI 기본값·서버 파일 경로·정규화 로직은 넣지 않는다. 이 시점에는 소비처 전환 없이 shared만 정비하므로 런타임 영향이 없다.

1-2GeneralSettings 소비처 전환

백엔드·프런트의 GeneralSettings 관련 import를 shared로 전환하고 로컬 중복 선언을 삭제한다. 기존 정규화·기본값 동작(서버측 기본값 채움, 프런트 UI 기본값)은 각 영역에 남긴 채 타입 참조만 바꾼다. 로컬 settings 타입 소비 파일이 68개이므로, 전환 후 남은 로컬 참조는 재export shim으로 유지하고 각 도메인 전환 때 걷어낸다.

검증: verify:user-db-smoke · verify:header-navigation-settings-contracts (backend) + 워크스페이스 타입 검사

1-3 ~ 1-6도메인 순차 전환 — tagger → kaloscope → llm → appearance

도메인당 커밋 1개. 각 커밋에서 (a) shared에 해당 도메인 wire 계약 이동, (b) 백엔드 라우트를 도메인 경계로 정렬(backend/src/routes/settings.ts:56-673의 18개 라우트·5개 하위 라우터: appearance / media / dataRematch / rating / runtime), (c) frontend/src/lib/api-settings.ts의 해당 도메인 API 함수(총 52개 export)를 같은 경계의 클라이언트 모듈로 분리, (d) 해당 도메인 재export shim 제거까지 완료한다.

검증: 위 backend 2종에 더해 verify:thumbnail-default-settings-contracts (backend) · verify:settings-folder-selection-contracts · verify:settings-paged-list-progress-contracts · verify:thumbnail-settings-ui-contracts (frontend)
회귀 가드: 라우트 경로·메서드·응답 형태는 그대로 두고 파일 위치만 옮긴다. 하위 라우터 mount 순서(settings.ts:669-673)를 바꾸지 않는다. 설정 API는 게스트/권한 경계와 무관하지 않으므로 라우트 이동 시 기존 인증 미들웨어 적용 범위를 커밋마다 diff로 확인한다.

완료 기준

  • 설정 API wire contract가 shared 한 소스에서 나오고, shared 소비처가 0에서 실사용으로 전환된다.
  • 프런트·백엔드 로컬 settings 타입에는 UI view model과 서버 런타임 전용 타입만 남는다.
  • 겹치던 54개 export 이름이 도메인별로 shared에 수렴하고 재export shim이 남아 있지 않다.

Phase 2 — GenerationHistory query/command 분리

backend/src/models/GenerationHistory.ts(1,056줄, 그래프 연결 51개)에서 조회 저장소와 쓰기 서비스를 분리한다. 목표 구조는 HistoryQueryRepository(필터 빌더·목록·상세·통계·미디어 projection) + HistoryCommandService(생성·상태 전이·오류·삭제 후 캐시 무효화 → 이벤트 발행 → 보존 호출을 한 순서로) + 중립 타입 모듈이다.

2-1필터 빌더 단일화

목록 조회와 통계 조회에 각각 있는 조건 조립(GenerationHistory.ts:229-276, :353-389)을 하나의 필터 빌더로 합친다. 합치기 전에 두 경로가 생성하는 SQL·바인딩을 대표 필터 조합별로 비교해 동등성을 확인하고, 차이가 있으면 의도된 차이인지 판정을 남긴다.

2-2HistoryQueryRepository 추출

목록·상세·통계 조회와 결과 미디어 projection(:728-920)을 조회 저장소로 옮긴다. 미디어 표시 정책(가시성·게스트 소유자 스코프)은 로직 변경 없이 함께 이동한다.

회귀 가드: 08-09에 게스트 히스토리 썸네일 403을 소유자 스코프 가드로 고쳤다. projection 이동 시 이 가드 경로가 유지되는지 확인하고, /recent·/statistics에는 계정 스코프가 없으므로 미디어 mount에 blanket bypass를 넣지 않는다.

2-3HistoryCommandService 추출

생성·상태 전이·오류·삭제와 그 부수효과(카운트 캐시 무효화, SSE 이벤트 발행 :17-48, 337, 439, 460, 538, 보존 정리 호출 :443, 462, 539, 571)를 쓰기 서비스로 옮기고 실행 순서를 코드에 명시한다. 이동 전에 상태 변경 메서드별 이벤트 발행 여부 표를 만들어 이동 후와 대조한다.

회귀 가드: 08-08에 "히스토리가 생성중에 멈춤" 회귀의 원인이 postprocess ready-flip과 update()가 SSE 이벤트를 발행하지 않던 것이었고 watchdog poll로 보완되어 있다. 쓰기 경로 이동 시 (a) 모든 상태 전이의 이벤트 발행 계약을 보존하고 (b) watchdog poll 경로를 제거하거나 우회하지 않는다.

2-4중립 타입 이동 — ServiceType, GenerationStatus

두 타입을 모델 밖의 타입 모듈로 옮겨 runtimeEventPublishers.ts → generationQueue.ts → GenerationHistory.ts 그래프상 순환(현재 type-only)을 함께 제거한다.

검증 (Phase 전체, 각 커밋마다): verify:queue-hot-path-contracts · verify:queue-wakeup-smoke · verify:queue-routing-smoke · verify:queue-cancel-protocol-contracts · verify:queue-eta-contracts · verify:result-retention-contracts (backend) + verify:generation-history-feed-progress-ui-contracts (frontend)

완료 기준

  • 히스토리 필터 SQL이 한 빌더에서 나온다.
  • 쓰기 순서(캐시 무효화 → 이벤트 → 보존)가 command 서비스 한 곳에 모이고, 상태 전이별 이벤트 발행 표와 실제 코드가 일치한다.
  • 모델 파일에는 순수 데이터 접근만 남고, 런타임 이벤트 계층 직접 참조가 없다.

Phase 3 — 미디어 백그라운드 처리 단계 분리

backend/src/services/backgroundProcessorService.ts(1,013줄)를 파일 단위 processor와 배치 오케스트레이터로 나눈다. public 메서드 시그니처와 DB 상태 전이는 전 과정에서 불변이다.

3-1이미지 processor 모듈 추출

:553-875 중 이미지 경로(접근 확인 → 형식 판별 → 해시 → 중복 연결 → 메타데이터 row → 썸네일)를 별도 모듈로 옮긴다. 단일 미디어 진입점(:223-393)은 새 모듈을 호출하는 형태로 유지한다.

3-2동영상 processor 모듈 추출

동영상 해시·포스터 생성 경로를 같은 방식으로 옮긴다.

회귀 가드: 포스터는 08-08 조사에서 496bd9ce 이후 미사용으로 확인된 영역과 접해 있다. 추출 시 현재 동작을 그대로 옮기되, 포스터 생성·소비 여부에 대한 판단 변경은 이 Phase 범위 밖으로 둔다.

3-3단계 결과 계약 도입

각 후처리 단계가 { stage, status, retryable, error } 형태의 명시적 결과를 반환하게 해 실패 위치를 기록한다. 자동 분류·그룹 할당(:966-1012)·자동 태그는 해시 저장 성공 뒤 호출되는 후처리 단계로 유지하고, 한 단계 실패가 이전 성공을 되돌리지 않는 현재 멱등성을 보존한다.

3-4배치 오케스트레이터 축소

배치 서비스(:397-548)에는 미처리 목록 조회, 동시성 제한, HTTP 양보, 진행 상태, 무진행 감지, WAL 정리, 재예약, 강제 중지만 남긴다.

회귀 가드: 워처 연계부를 건드릴 때 08-09 수정(마이그레이션 033: watcher_polling_interval null 기본값 + 2초 하한, chokidar 폴링 강제 금지)을 되돌리지 않는다. 서버 listen을 워처 부팅에 블로킹시키지 않는 43d39a1d 동작도 유지한다.
검증 (Phase 전체, 각 커밋마다): verify:invalid-media-processing-contracts · verify:media-postprocess-visibility · verify:video-optimization · verify:sqlite-wal-maintenance-contracts · verify:watched-folder-scan-efficiency-contracts (backend)

완료 기준

  • 배치 서비스는 동시성·중지·잠금·재예약만 담당하고, 이미지/동영상 처리 단계는 독립적으로 검증 가능하다.
  • 부분 실패 시 어느 단계에서 멈췄는지 결과 객체로 남는다.
  • 배포 확인: 소규모 개발 사본은 부하 문제가 재현되지 않으므로, Phase 3 완료 후 대형 배포본에서 대량 폴더 감시 + 배치 처리 시나리오를 확인한다.

Phase 5 — 검증 자산 정비 (병행 트랙)

verify 자산(150개 파일·25,654줄)은 강점이므로 버리지 않고, 각 Phase가 옮기는 영역의 스크립트를 함께 정리한다.

  • Phase 규칙(1~4에 적용): 영역을 옮길 때 해당 verify를 동작 검증(임시 DB·실제 함수 실행)과 구조 검증(금지 import·금지 시그니처·번들 예산)으로 나누어 새 파일 경계에 맞춘다. 함수 본문 문자열 단언은 이때 실행형으로 바꾸거나 삭제 판정을 남긴다. 우선 대상: backend/src/scripts/verifyGenerationQueueHotPathContracts.ts(DB 검증과 소스 정규식 혼재, Phase 2에서), frontend/src/scripts/verifyModuleGraphExecutionPanelContracts.ts(647줄 문자열 검사, Phase 4에서).
  • 마무리 커밋 1개: 반복되는 source() 읽기, 함수 추출, assertion 출력만 작은 공용 helper로 합친다. 표준 test runner나 별도 harness는 도입하지 않는다.
  • 원칙: 권한·데이터 무결성·마이그레이션·큐 상태 전이는 실행형 검증 우선, 정적 소스 검사는 구조 금지 규칙에만 사용한다.

완료 기준

  • Phase 1~4에서 옮긴 영역의 verify가 새 파일 경계를 가리키며 전부 통과한다.
  • 고위험 계약이 함수 본문 문자열 매칭에 의존하지 않는다.

Phase 6 — 후순위 백로그 (선택, 별도 판단)

내장 시스템 모듈 정의 레지스트리 분할

backend/src/database/userSettingsBuiltinModuleDefinitionData.ts(2,330줄, 37개 정의·10개 카테고리)를 카테고리별 파일로 나누고 현재 순서를 보존하는 aggregator로 합친다. 검증은 기존 verify:builtin-system-modules를 그대로 사용한다. 변경 충돌이 실제로 잦아질 때 착수한다.

백엔드 종료 수명주기 분리

backend/src/index.ts:619-777의 graceful shutdown coordinator와 middleware/bootstrap 조립만 분리한다. startServer() 전체 재작성은 하지 않으며, 종료 순서(파일 워처 → 스케줄러 → 임시 파일 → daemon → DB)를 그대로 보존한다.

범위 제외 — 이번 계획에서 하지 않는 것

  • 번역 리소스 대형 파일 분리 (정적 사전 성격, 분리 실익 없음)
  • any 전역 치환 (외부 경계 스키마 작업과 함께 별도 진행)
  • Graphify 순환의 즉시 수정 (Phase 2-4의 타입 이동으로 자연 해소)
  • 새 테스트 플랫폼·harness 도입
  • DB 스키마 변경·마이그레이션 (이 계획에는 없음)
  • 동영상 포스터 생성·소비 정책 변경 (perf 후속 작업에서 별도 판단)

커밋·검증·롤백 규칙

커밋 전
해당 커밋 단위의 verify 명령 + 워크스페이스 타입 검사 통과. Phase별 회귀 가드 체크리스트 확인. 커밋 메시지는 기존 관례(refactor(scope): …)를 따르고 판정 사항(정본 확정 등)을 본문에 남긴다.
커밋 단위
이 문서의 태그(1-1, 2-3, …) 하나가 커밋 하나다. 두 태그를 한 커밋에 합치지 않는다. wire·DB 계약이 불변이므로 어떤 커밋도 단독 revert로 롤백 가능해야 한다.
Phase 종료
Phase의 전체 verify 세트를 한 번 더 실행하고 완료 기준을 대조한다. Phase 3 종료 시에는 대형 배포본 확인을 포함한다. 다음 Phase는 그 후에만 연다.
문제 발생 시
회귀가 확인되면 원인 커밋만 revert하고 Phase를 중단 상태로 유지한다. 여러 영역이 동시에 열려 있지 않으므로 회귀 원인은 항상 마지막 Phase 안에 있다.

전체 완료 기준

  • 설정 API wire contract가 shared 한 소스에서 나오고 프런트·백엔드 로컬 타입은 UI/런타임 전용만 남는다.
  • 생성 히스토리 필터 SQL이 한 빌더를 사용하며 쓰기 순서와 이벤트·보존 호출이 한 서비스에 모인다.
  • 백그라운드 미디어 배치 서비스가 동시성·중지·재예약만 담당하고 이미지/동영상 처리 단계는 독립 검증 가능하다.
  • module graph node card에 새 operation key를 추가할 때 본체 조건 체인을 수정하지 않아도 된다.
  • 고위험 계약은 실제 함수/DB 기반 검증으로 보호되고, 정적 소스 검사는 구조 금지 규칙에 집중한다.
  • 각 단계는 독립 커밋과 기존 영역별 검증을 통과한 뒤 다음 단계로 넘어간다.
